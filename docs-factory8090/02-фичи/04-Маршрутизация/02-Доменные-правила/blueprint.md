# Доменные правила

> Источник: https://factory.8090.ai/project/992274e4-1c6b-4d44-8c22-e4c038e690c2/blueprints/0459c972-20c3-4c1c-8373-4177564d0085

## Обзор фичи

Фича формирует доменные правила маршрутизации для конфигурации sing-box и предоставляет renderer-интерфейс для их управления. Она связывает сохранённые `DomainRule` с правилами `route.rules`, которые вставляются перед базовым маршрутом. Соответствующие требования описаны в @Доменные правила.

## Композиция компонентных blueprints

Фича использует `tunController` как владельца генерации конфигурации VPN. `domainRoutingService` передаёт ему сгенерированные правила, а `DomainRouting` предоставляет управление через IPC. Отдельного Component Blueprint для этой фичи не создано: наблюдаемая реализация состоит из feature-specific сервиса, UI-компонента и генератора конфигурации.

## Компоненты, специфичные для фичи

### Основной процесс

```component
name: DomainRoutingService
container: Electron Main Process
responsibilities:
	- Хранит `DomainRule` в electron-store с именем domain-routing.
	- Выполняет добавление, изменение, удаление, импорт и изменение порядка правил.
	- Нормализует шаблоны доменов, проверяет действия vpn, direct и block и ограничивает длину шаблона 253 символами.
	- Генерирует правила sing-box с outbound direct-out, proxy-out или block-out либо с действием reject для блокировки.
	- Регистрирует IPC-каналы domain-routing:list, domain-routing:add, domain-routing:update, domain-routing:delete, domain-routing:reorder, domain-routing:import и domain-routing:browse-file.
	- При изменении правила на активном туннеле запрашивает перезапуск с последними параметрами.
```

`DomainRoutingService` передаёт результат `domainRulesToSingboxRules` в #TunController. Правила сортируются по возрастанию `priority`, поэтому порядок массива задаёт поведение first-match-wins в sing-box.

### Renderer

```component
name: DomainRouting
container: Electron Renderer Process
responsibilities:
	- Загружает список доменных правил через IPC и отображает его по приоритету.
	- Даёт пользователю форму добавления и редактирования шаблона и действия.
	- Поддерживает удаление и drag-and-drop изменение порядка правил.
	- Открывает выбор файла и запускает импорт списка доменов.
	- Показывает действия через VPN, напрямую и блокировать, а также счётчик срабатываний из `DomainRule`.
```

#DomainRouting взаимодействует с #DomainRoutingService через preload API. Renderer обновляет локальное состояние после успешной операции и не управляет конфигурацией sing-box напрямую.

### Генерация конфигурации

```component
name: TunController
container: Electron Main Process
responsibilities:
	- Вызывает генерацию доменных route rules при построении sing-box-конфигурации.
	- Вставляет пользовательские доменные правила в `route.rules` перед catch-all и другими маршрутами в соответствии с порядком генерации.
	- Перезапускает активный туннель при изменении доменного правила, если активное подключение сообщает running.
```

## Системные контракты

### Ключевые контракты

* `DomainRule` имеет `id`, `pattern`, `action`, `priority` и `hitCount`; допустимые действия: vpn, direct и block.
* Шаблон `*.example.com` преобразуется в `domain_suffix: [".example.com"]` и предназначен для поддоменов без bare apex.
* Шаблон с точкой преобразуется в `domain` и `domain_suffix`, поэтому текущее поведение включает точный домен и поддомены. Это подтверждает находку F-008 из S07 и требует отдельного решения о соответствии точному сопоставлению.
* Шаблон без точки преобразуется в `domain_keyword`.
* Правила сортируются по приоритету до генерации и должны быть вставлены до базового маршрута.
* Пустой список доменных правил даёт пустой набор дополнительных route rules.
* Счётчики срабатываний хранятся в интерфейсе, но фактическая запись срабатываний удалена. В текущей реализации они остаются равными нулю. Это находка F-011 из S07.
* Изменение правила при активном туннеле запускает попытку hot reload через перезапуск защиты. Реализация требует проверки на устройстве, как указано в документации аудита о частичном live-apply.

### Интеграционные контракты

* Renderer вызывает IPC-операции управления доменными правилами через preload API.
* `TunController` получает правила через `generateDomainRouteRules` и добавляет их в `route.rules` с outbound `direct-out`, `proxy-out` либо reject для block.
* Импорт принимает текстовый файл с одним шаблоном на строку, пропускает пустые строки, назначает импортированным правилам action direct и добавляет их после существующих правил.
* Обогащение доменов Chromium включается отдельной настройкой, сохраняет результаты локально и не закрепляет IP-адрес назначения. Это соответствует находке F-177 из S17 и не является механизмом маршрутизации правил.

## Записи архитектурных решений

### ADR-001: Приоритет пользователя перед базовым маршрутом

**Контекст:** Пользовательские доменные правила должны переопределять базовый маршрут через VPN для совпавшего домена.

**Решение:** Генерировать правила в порядке возрастания `priority` и передавать их в `route.rules` перед catch-all правилами.

**Последствия:** Результат зависит от корректного порядка правил и от правил Smart RU, которые могут быть сгенерированы рядом. На это указывает F-009 из S07: переопределение «карты через VPN» может проиграть более раннему правилу госдоменов RU.

### ADR-002: Оставить действия direct, vpn и block

**Контекст:** Код и UI поддерживают три действия, а родительская фича явно описывает только исключения маршрута.

**Решение:** Зафиксировать все три наблюдаемые действия в дочерней фиче. Действие block генерирует reject.

**Последствия:** Требования отражают фактическое поведение, но продуктовая семантика блокировки остаётся вопросом для подтверждения.
