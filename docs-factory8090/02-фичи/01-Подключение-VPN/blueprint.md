# Подключение VPN

## Сводка функции

Функция связывает управление защитой VPN из Dashboard и Tray с единым жизненным циклом туннеля. Она выполняет запуск и остановку защиты, передаёт состояние подключения и отображает результат пользователю в соответствии с требованиями `REQ-CONN-001`–`REQ-CONN-004`.

## Состав архитектуры функции

### Основной процесс Electron

`index.ts` принимает IPC-запросы `start-tun` и `stop-tun`, выбирает путь запуска из Dashboard или Tray и координирует `#TunController` с состоянием Tray и renderer. Для упакованного приложения процесс использует блокировку единственного экземпляра.

### Контроллер туннеля

`#TunController` выполняет preflight, подготавливает runtime, проверяет конфигурацию через `sing-box check`, запускает процесс с повышением прав, ожидает TUN, включает сетевые меры защиты и watchdogs, а при остановке выполняет согласованную очистку.

### Клиентский Dashboard и Tray

Dashboard получает события состояния через preload IPC и показывает переходные состояния, IP, время работы и трафик. `#TrayController` предоставляет действия включения и выключения защиты, показывает статус, IP и скорость трафика и использует те же обработчики жизненного цикла.

## Компоненты, специфичные для функции

```component
name: TunController
container: Electron Main Process
responsibilities:
	- Выполняет единый жизненный цикл запуска и остановки TUN-туннеля.
	- Проверяет готовность конфигурации и TUN перед переходом в состояние работы.
	- Управляет процессами sing-box и Xray, когда для REALITY выбран Xray.
	- Передаёт переходные и итоговые состояния в основной процесс через callback состояния.
```

```component
name: ProtectionLifecycleCoordinator
container: Electron Main Process
responsibilities:
	- Обрабатывает IPC-команды запуска и остановки защиты.
	- Выбирает локальный прокси или прямой VPN согласно настройкам подключения.
	- Синхронизирует состояние Dashboard, Tray и контроллера туннеля.
	- Запускает сетевой baseline, мониторинг IP, трафика и защитные откаты в границах жизненного цикла.
```

`#ProtectionLifecycleCoordinator` передаёт параметры подключения в `#TunController`. При запуске контроллер сначала проверяет конкурирующие TUN и готовит runtime, затем сообщает о работающем туннеле. При остановке координатор останавливает связанные наблюдатели и передаёт остановку контроллеру, который выполняет очистку процессов, TUN и сетевых изменений.

```component
name: TrayController
container: Electron Main Process
responsibilities:
	- Отображает состояние защиты, IP и скорости трафика в системном Tray.
	- Предоставляет команды включения и выключения защиты.
	- Передаёт ошибки действий Tray в журнал приложения.
```

`#TrayController` вызывает `#ProtectionLifecycleCoordinator`, поэтому действие из Tray использует тот же жизненный цикл, что и действие из Dashboard. Ошибки действия Tray сейчас логируются, а пользовательское уведомление зависит от вызывающего пути.

```component
name: DashboardConnectionView
container: Electron Renderer
responsibilities:
	- Отображает состояние подключения, работы, отключения и ошибки.
	- Отображает IP, время работы и сведения о трафике, когда они доступны.
	- Отправляет команды запуска и остановки через preload IPC.
```

`#DashboardConnectionView` получает событие `tun-status-changed` через preload IPC. Основной процесс остаётся владельцем фактического состояния туннеля, а renderer отображает его и не создаёт отдельный жизненный цикл.

```component
name: CompetingTunWatchdog
container: Electron Main Process
responsibilities:
	- Проверяет появление чужого VPN/TUN во время работы собственного TUN.
	- Проверяет состояние сразу после запуска наблюдения и затем каждые 15 секунд.
	- Передаёт предупреждение о конкурирующем туннеле в журнал, уведомление и renderer.
```

`#CompetingTunWatchdog` получает управление от `#TunController`. При обнаружении другого TUN он предупреждает пользователя и не останавливает собственный туннель автоматически.

## Системные контракты

### Ключевые контракты

* Повторный запуск при уже работающем туннеле отклоняется.
* Одновременные запуск и остановка не должны создавать два независимых жизненных цикла. Остановка ожидает активный запуск в пределах предусмотренного периода ожидания.
* Успешный запуск публикует состояние `running`; остановка публикует переход через `stopping` и завершает жизненный цикл состоянием выключенной защиты.
* Ошибка запуска не должна оставлять пользователя без сообщения о том, что защита не включена.
* Конфигурация TUN использует IPv4-адрес `192.168.250.253/30`, строгую маршрутизацию, перехват DNS и DoH через proxy-out; итоговый маршрут направляется через proxy-out.
* Для REALITY автоматически выбирается Xray. Это решение относится к текущей реализации и не описывает будущие дочерние функции.
* При работающем собственном TUN появление чужого TUN вызывает предупреждение и не приводит к автоматической остановке.
* Упакованное приложение ограничивает работу одним экземпляром, чтобы два процесса не управляли одним kill-switch, TUN и manifest одновременно.

### Контракты интеграции

* IPC `start-tun` запускает защиту через локальный прокси с параметрами адреса и типа прокси.
* IPC `stop-tun` запускает остановку текущей защиты.
* Событие `tun-status-changed` передаёт renderer переходные и рабочие состояния, включая конкурирующий TUN.
* Событие `soft-status-changed` сообщает о состоянии мягкого пути локального прокси.
* Tray-команды `onStart` и `onStop` подключены к тому же координатору жизненного цикла.

## Известные проблемы

По [@Журналу аудита кода VPN Tunnel Enforcer](https://factory.8090.ai/project/992274e4-1c6b-4d44-8c22-e4c038e690c2/knowledge-base/eb72dd10-8123-4865-a5d5-01d28ab9de94) известны следующие проблемы границы функции:

* F-012: PID в статусе туннеля всегда `null`.
* F-018: PID-файл из `managedChildProcess.ts` не используется при запуске sing-box.
* F-022: очистка старого runtime может остановить Xray, запущенный для прямого VPN.
* F-131: необработанное исключение main-процесса не завершает процесс.
* F-133: при выходе возможны гонки очистки.
* F-019: `tunController.ts` и `main/index.ts` являются чрезмерно большими файлами.

## Архитектурные решения

### ADR-001: Единый жизненный цикл туннеля

**Контекст:** Dashboard и Tray должны управлять одной защитой и показывать согласованное состояние.

**Решение:** Основной процесс Electron владеет жизненным циклом через `#ProtectionLifecycleCoordinator` и `#TunController`; Dashboard и Tray используют этот контур через IPC и действия Tray.

**Последствия:** Состояние и очистка централизованы. Большие файлы основного процесса и контроллера остаются известным техническим долгом.

### ADR-002: Защита от конкурирующих TUN

**Контекст:** Второй TUN может конфликтовать с маршрутами и DNS во время работающей защиты.

**Решение:** Выполнять preflight перед запуском и периодически проверять чужие TUN во время работы. При обнаружении показывать предупреждение без автоматической остановки.

**Последствия:** Пользователь получает предупреждение и сохраняет контроль над остановкой. Конфликт маршрутов может сохраняться до действия пользователя.
