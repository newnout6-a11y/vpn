# Альтернативное ядро mihomo (план)

## Статус blueprint

Целевая архитектура по плану. В текущем коде нет `CoreAdapter`, `SingBoxAdapter` или `MihomoAdapter`. Blueprint не описывает реализованную поддержку mihomo.

## Feature Summary

Эта фича описывает целевую подготовку второго ядра VPN после выделения общей границы ядра. Она связывает требования REQ-CONN-CORE-001, REQ-CONN-CORE-002 и REQ-CONN-CORE-003 с планируемыми адаптерами, сохранением режима sing-box-first и диагностикой runtime-specific деталей.

Текущая реализация остаётся основанной на sing-box. Реальная точка расширения `proxyEngine.ts` выбирает sing-box или Xray для upstream proxy, но не является общей границей ядра и не даёт mihomo runtime.

## Component Blueprint Composition

Общая граница ядра пока не представлена отдельным Component Blueprint. После её создания эта фича должна использовать её для согласования операций генерации конфигурации, подготовки runtime, запуска, остановки, состояния, health, диагностики и очистки.

`proxyEngine.ts` рассматривается только как существующая точка выбора upstream proxy. В текущем состоянии он разрешает режимы `auto`, `sing-box` и `xray`; режим `auto` направляет REALITY-сценарии через Xray, а остальные поддержанные случаи через sing-box. Этот выбор не должен трактоваться как поддержка mihomo.

## Feature-Specific Components

```component
name: CoreAdapter
container: Main Process
responsibilities:
	- Планируемо предоставляет единую границу операций ядра VPN: генерация конфигурации, подготовка runtime, запуск, остановка, состояние, health, диагностика и очистка.
	- Передаёт engine-specific ошибки и диагностические сведения вызывающим компонентам.
	- Не реализован в текущем коде.
```

```component
name: SingBoxAdapter
container: Main Process
responsibilities:
	- Планируемо сохраняет текущее поведение sing-box за границей `CoreAdapter`.
	- Сохраняет совместимость с существующими сценариями запуска, остановки и очистки.
	- Не реализован в текущем коде.
```

```component
name: MihomoAdapter
container: mihomo sidecar, план
responsibilities:
	- Планируемо адаптирует mihomo к границе `CoreAdapter` после проверки самой границы.
	- Изолирует экспериментальный runtime от жизненного цикла sing-box.
	- Не реализован в текущем коде.
```

`CoreAdapter` должен стать точкой зависимости для будущего `SingBoxAdapter` и `MihomoAdapter`. До этого текущие sing-box-specific операции остаются в существующих компонентах main process, включая `tunController` и связанные с ним пути профилей, выбора серверов и диагностики.

## System Contracts

### Key Contracts

* До появления проверенного `CoreAdapter` приложение работает в режиме sing-box-first.
* Прототип mihomo не запускается до появления и проверки границы ядра.
* `SingBoxAdapter` не меняет пользовательское поведение запуска, остановки и очистки sing-box после extraction.
* Engine-specific ошибки не заменяются общей ошибкой туннеля без сохранения диагностических деталей.
* Прототип mihomo не становится пользовательским runtime по умолчанию без отдельного решения о поддержке, диагностике и безопасном жизненном цикле.

### Integration Contracts

* Планируемый `CoreAdapter` должен принимать операции, необходимые для генерации конфигурации, подготовки runtime, запуска, остановки, получения состояния, health, диагностических hooks и очистки.
* Будущий `MihomoAdapter` должен работать через ту же границу, что и `SingBoxAdapter`, и не требовать прямого смешивания mihomo-specific логики с sing-box lifecycle.
* `proxyEngine.ts` остаётся текущим контрактом выбора upstream proxy между sing-box и Xray. Расширение его списка режимов до mihomo не входит в этот план без отдельного решения.
* Точные конфигурационные схемы mihomo, способ доставки бинарного runtime, процессная граница sidecar, mapping состояний и формат диагностических данных пока не определены.

## Architecture Decision Records

### ADR-001: Сначала граница ядра, затем mihomo

**Context:** Код приложения тесно связан с sing-box, а roadmap прямо откладывает mihomo до появления engine abstraction. Раннее добавление второго runtime увеличит число failure modes и усложнит диагностику.

**Decision:** Сначала выделить `CoreAdapter` и сохранить текущее поведение через `SingBoxAdapter`. После этого оценивать изолированный `MihomoAdapter` и mihomo sidecar как прототип.

**Consequences:** Текущая реализация остаётся sing-box-first. Mihomo не добавляет пользовательскую возможность на этом этапе, зато сохраняется контролируемый путь к эксперименту без смешивания двух runtime.

### ADR-002: Сохранить runtime-specific диагностику

**Context:** Разные ядра будут иметь разные ошибки запуска, health, остановки и очистки. Общая ошибка без контекста не позволит определить источник сбоя.

**Decision:** Планируемая граница должна передавать диагностические hooks и сохранять сведения, специфичные для runtime.

**Consequences:** Контракт адаптера будет сложнее, чем единый generic error, зато анализ отказов и проверка регрессий останутся возможными.

### ADR-003: Не связывать mihomo с текущим выбором proxy engine

**Context:** `proxyEngine.ts` уже выбирает sing-box или Xray для upstream proxy, но в коде нет общей engine abstraction и поддержки mihomo.

**Decision:** Использовать `proxyEngine.ts` как документированную точку расширения, не выдавая её за реализацию `CoreAdapter` и не добавляя mihomo в текущий выбор.

**Consequences:** Blueprint связан с реальной точкой расширения, но не создаёт ложных code links на несуществующие адаптеры. Поддержка mihomo остаётся целевой архитектурой.
