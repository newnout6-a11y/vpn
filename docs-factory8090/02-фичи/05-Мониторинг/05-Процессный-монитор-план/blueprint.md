# Процессный монитор трафика (план)

> Источник: https://factory.8090.ai/project/992274e4-1c6b-4d44-8c22-e4c038e690c2/blueprints/dcc24717-872a-4a73-ab91-2cac5cb6cad3

## Feature Summary

Статус функции: **план**. Функция должна показывать постоянную атрибуцию сетевой активности к процессам: имя приложения, направление и доступный объём трафика. Она должна объединять сетевые и DNS-события, чтобы пользователь понимал, какое приложение обращается к какому домену или IP-адресу.

Текущий код не реализует эту функцию. `vpnte-etw-sidecar.exe` существует как часть форензики трафика по запросу: он собирает нормализованные ETW-артефакты для диагностической сессии и не является доказательством постоянного мониторинга. План в `IDEAS.md` отдельно требует перевести sidecar в постоянный режим, сопоставлять PID с именем процесса, объединять DNS и сетевые события и передавать результат в интерфейс.

## Component Blueprint Composition

Планируемая функция должна использовать существующий механизм ETW-сайдкара только после изменения его жизненного цикла с диагностической сессии на постоянное наблюдение. В текущем коде `trafficForensics.ts` запускает и останавливает sidecar вместе с сессией форензики, а RFC описывает нормализованные категории `tcp`, `dns`, `wfp`, `afd` и `webio`. Эти текущие возможности относятся к форензике и не описывают готовый компонент процессного мониторинга.

Планируемое решение должно получать DNS-данные из журналов `sing-box`, сетевые TCP/UDP-события из ETW/WFP и передавать объединённый результат в renderer через IPC. Точные компоненты, IPC-каналы, формат объединённого потока и границы хранения не подтверждены кодом и остаются открытыми вопросами.

## Feature-Specific Components

Планируемые компоненты ниже не существуют в текущем коде. Их состав отражает только подтверждённый план из `IDEAS.md` и не является утверждением о реализации.

```component
name: ProcessTrafficMonitor
container: Electron main process, renderer
responsibilities:
	- Планировать постоянное наблюдение сетевых метаданных по процессам во время выбранного жизненного цикла VPN.
	- Передавать в интерфейс агрегированные данные о процессе и направлении после подтверждённого сопоставления.
	- Показывать неполную атрибуцию, если источник событий или сопоставление недоступны.
```

```component
name: ProcessIdentityResolver
container: ETW sidecar
responsibilities:
	- Планировать сопоставление `ProcessId` с `ProcessName`.
	- Кэшировать сведения о процессе, чтобы уменьшить повторные обращения к системе.
	- Не выдавать имя процесса, если PID нельзя надёжно сопоставить.
```

```component
name: TrafficFlowCorrelator
container: Electron main process
responsibilities:
	- Планировать объединение DNS-событий из `sing-box.log` с TCP/UDP-событиями ETW/WFP.
	- Сопоставлять события по доступным времени, адресу и признакам соединения.
	- Сохранять различие между подтверждённым доменом, IP-адресом и отсутствующим результатом.
```

## System Contracts

### Key Contracts

* До реализации функция имеет статус плана и не должна отображаться как доступный постоянный монитор.
* Форензика трафика и процессный монитор имеют разные жизненные циклы. Запуск ETW-сайдкара для диагностической сессии не включает процессный монитор.
* Базовый режим должен работать с метаданными и не требовать сохранения содержимого пакетов.
* Неполный источник событий, потеря ETW-событий и неоднозначное сопоставление должны быть видимы как неполное наблюдение.
* Агрегирование, размер накопленных данных, срок хранения и ротация должны быть ограничены политикой, которая пока не определена.

### Integration Contracts

* Планируемый вход: нормализованные TCP/UDP-события ETW/WFP с доступными PID, адресами, портами и протоколами.
* Планируемый вход: DNS-события из `sing-box.log` с доступными именами и результатами разрешения.
* Планируемый выход: объединённые записи для интерфейса с процессом, направлением, протоколом, доменом или IP-адресом и агрегированными показателями, если они подтверждены.
* Точные IPC-каналы, схема записи, порядок событий, задержка корреляции и поведение при перезапуске пока не определены.
* Процессный монитор не должен включать в свой контракт диагностические PCAP/ETL и другие артефакты форензики, если для этого нет отдельного решения.

## Architecture Decision Records

### ADR-001: Процессный монитор остаётся планом

**Context:** В `IDEAS.md` описан будущий мониторинг по процессам, а текущий код запускает ETW-сайдкар только в рамках форензики. RFC также описывает Phase 4 как реализованный sidecar и отдельно оставляет корреляцию потоков в Phase 5.

**Decision:** Зафиксировать функцию как планируемую. В требованиях и blueprint не утверждать наличие постоянного сбора, готовой PID-атрибуции, готовой корреляции или готового UI.

**Consequences:** Документы сохраняют границу между существующей форензикой по запросу и будущим постоянным монитором. Реализация потребует отдельных решений по режиму включения, разрешениям Windows, приватности, производительности и хранению.

### ADR-002: Метаданные вместо содержимого пакетов в базовом режиме

**Context:** План требует постоянного наблюдения, а RFC для форензики предупреждает о чувствительности payload, доменов, IP и DNS-запросов. Полная атрибуция процесса и выбор системного механизма ещё не подтверждены.

**Decision:** В качестве планового ограничения описывать метаданные сетевых событий и не фиксировать сохранение payload как часть базового режима.

**Consequences:** Снижается риск раскрытия содержимого трафика, но остаются вопросы о полноте PID-атрибуции, задержке корреляции, объёме данных и требуемых разрешениях.
