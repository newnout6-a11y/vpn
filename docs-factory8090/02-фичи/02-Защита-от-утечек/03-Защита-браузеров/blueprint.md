# Защита браузеров

## Feature Summary

Функция реализует проверку IP и WebRTC-адресов во внешнем браузере и применяет настройки защиты от WebRTC/IP-утечки к обнаруженным профилям Chromium-браузеров и Firefox. Она соответствует @Защита браузеров и используется как дочерняя часть @Защита от утечек.

## Component Blueprint Composition

Функция получает состояние туннеля и публичный адрес через существующий IPC-контракт приложения. #BrowserIpCard запускает браузерные проверки и вызывает `getPublicIp`, а также команды применения и отката защиты через `window.electronAPI`.

## Feature-Specific Components

### Main process

```component
name: BrowserHardening
container: Electron main process
responsibilities:
	- Обнаруживает поддерживаемые профили Yandex Browser, Google Chrome, Microsoft Edge, Brave, Chromium, Vivaldi, Opera и Firefox.
	- Сохраняет registry-ветки и файлы профилей в `BackupManifest` перед изменением.
	- Записывает `WebRtcIPHandlingPolicy=disable_non_proxied_udp` в поддерживаемые ветки Windows Registry и подтверждает запись обратным чтением.
	- Обновляет Chromium `Preferences` и Firefox `user.js` параметрами WebRTC и проверяет результат чтением.
	- Восстанавливает registry-ветки и файлы профилей из манифеста; при ошибке сохраняет манифест для повторной попытки.
```

### Renderer

```component
name: BrowserIpCard
container: Electron renderer
responsibilities:
	- Получает публичные IPv4 и IPv6 через браузерные HTTP-запросы с тайм-аутом.
	- Создаёт WebRTC peer connection с Google STUN и классифицирует кандидаты как локальные, публичные или mDNS.
	- Сравнивает браузерный IPv4 с адресом main-процесса и формирует результат `BrowserIpCheck`.
	- Показывает пользователю результат проверки, предупреждения, действия применения и отката.
	- Отменяет незавершённую проверку и не принимает результат размонтированного компонента.
```

#BrowserIpCard вызывает #BrowserHardening через IPC-контракты `applyBrowserLeakProtection` и `rollbackBrowserLeakProtection`. Результат операции содержит успешность, факт изменения, необходимость перезапуска, сообщение и подробности для журнала интерфейса.

## System Contracts

### Key Contracts

* Защита работает только на Windows. На других платформах операция возвращает неуспешный результат с объяснением недоступности.
* Если поддерживаемые профили не обнаружены, применение возвращает успешный результат без изменения настроек.
* Перед изменением существующих registry-веток и файлов создаётся запись в `BackupManifest`.
* Запись Chromium policy считается подтверждённой только после read-back ожидаемого значения. В текущей реализации достаточно подтверждения одной ветки HKLM или HKCU, поэтому полное покрытие браузера не доказано.
* Успешное изменение или откат требует полного перезапуска внешних браузеров.
* Если исходный файл существовал, но backup отсутствует, откат не удаляет файл и возвращает неполный результат.
* При ошибке восстановления манифест не удаляется.
* Параллельные apply и rollback не сериализуются. Возможный конфликт манифеста и файлов профилей остаётся открытым вопросом.

### Integration Contracts

* `applyBrowserLeakProtection` возвращает `BrowserHardeningResult` с полями `success`, `changed`, `restartRequired`, `message` и `details`.
* `rollbackBrowserLeakProtection` использует тот же результат и восстанавливает состояние по `latest-browser-hardening.json`.
* Проверка браузера формирует `BrowserIpCheck` с браузерными IPv4/IPv6, адресом main-процесса, сравнением IPv4, списками WebRTC-адресов, mDNS-счётчиком, ошибкой и деталями.
* Dashboard размещает #BrowserIpCard на странице проверки состояния туннеля.
* Внешние запросы проверки используют `api.ipify.org`, `api.myip.com`, `api6.ipify.org` и `stun:stun.l.google.com:19302`. Их приватность, доступность и необходимость требуют отдельного решения.

## Architecture Decision Records

### ADR-001: Политики и файловые настройки для защиты WebRTC

**Context:** Аудит подтверждает применение настроек Chromium policy, Chromium `Preferences` и Firefox `user.js`, но не подтверждает полную Windows runtime-применимость при конфликте HKLM/HKCU или различиях конкретных браузеров.

**Decision:** Сохранять исходное состояние в манифесте, применять настройки к обнаруженным профилям и подтверждать записи доступным обратным чтением. Считать результат ограниченным подтверждением, пока Windows E2E не проверит конфликт политик и фактическое поведение браузеров.

**Consequences:** Настройки можно откатить, а ошибки записи видны пользователю. Полное browser coverage нельзя заявлять по результатам текущего runtime-пути.

### ADR-002: Проверка IP и WebRTC из renderer

**Context:** BrowserIpCard должна показать фактические адреса, видимые браузерному окружению, и сравнить их с адресом main-процесса.

**Decision:** Получать IPv4/IPv6 через внешние HTTP-сервисы и собирать WebRTC-кандидаты через Google STUN с отменой по тайм-ауту и сигналу компонента.

**Consequences:** Проверка отражает наблюдаемое поведение браузера и защищена от устаревшей записи результата. Она зависит от внешних сервисов, а влияние этой зависимости на приватность и доступность остаётся открытым вопросом.
