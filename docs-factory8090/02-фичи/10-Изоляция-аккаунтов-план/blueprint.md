# Изоляция аккаунтов в браузерных профилях (план)

> Источник: https://factory.8090.ai/project/992274e4-1c6b-4d44-8c22-e4c038e690c2/blueprints/790f1129-3f1f-4a2b-9e60-2cb317329ff0

## Feature Summary

Это целевая архитектура для @Изоляция аккаунтов в браузерных профилях (план). Функция должна создавать отдельные боксы, запускать поддерживаемый Chromium-браузер с отдельным каталогом данных и направлять его трафик через выбранный профиль сервера или прямой выход. Функция не реализована, поэтому данный блюпринт описывает предлагаемое состояние после реализации по черновому плану.

## Component Blueprint Composition

Функция должна использовать существующий механизм профилей серверов и общую конфигурацию VPN Tunnel Enforcer как источник параметров сетевого выхода. Конкретная точка интеграции и границы переиспользуемых компонентов требуют архитектурного решения.

Предлагаемая целевая композиция использует отдельный процесс sing-box для каждого запущенного бокса. Такой процесс получает конфигурацию выбранного профиля сервера, открывает локальный SOCKS5-вход и передаёт трафик бокса через соответствующий VPN-выход. Главный TUN-режим приложения остаётся отдельным. Вариант с одним общим процессом sing-box также описан в плане и не закрыт решением.

## Feature-Specific Components

### Управление боксами

```component
name: BrowserBoxManager
container: Electron main process
responsibilities:
	- Хранит и изменяет записи боксов в отдельном persistent store.
	- Создаёт, получает, перечисляет, обновляет и удаляет боксы.
	- Управляет командами запуска и остановки через `BrowserBox` contracts.
	- Сохраняет связь бокса с `ServerProfile` или прямым сетевым выходом.
```

### Среда выполнения бокса

```component
name: BoxRuntime
container: Electron main process
responsibilities:
	- Запускает и контролирует отдельный sing-box process для бокса.
	- Генерирует per-box `SingBoxConfig` с локальным SOCKS5-входом и выбранным VPN-выходом.
	- Ожидает готовность локального прокси перед запуском браузера.
	- Обнаруживает завершение браузера и останавливает связанный прокси-процесс.
```

`BrowserBoxManager` передаёт `BrowserBox` и `ServerProfile` в `BoxRuntime`. `BoxRuntime` подготавливает `SingBoxConfig`, затем передаёт браузеру локальный proxy endpoint и отдельный `UserDataDir`.

### Обнаружение браузеров

```component
name: BrowserDetector
container: Electron main process
responsibilities:
	- Находит установленные Chrome, Edge, Yandex Browser и Brave в Windows.
	- Возвращает доступные `BrowserInstallation` для выбора пользователем.
	- Выбирает первую найденную установку как значение по умолчанию.
```

### Страница боксов

```component
name: BoxesPage
container: Electron renderer process
responsibilities:
	- Показывает список боксов, их браузер, сетевой выход и состояние.
	- Предоставляет действия создания, запуска, остановки, удаления и изменения бокса.
	- Показывает время работы и размер каталога данных.
```

`BoxesPage` использует IPC bridge для вызова `BrowserBoxManager`. `BoxRow` представляет состояние одного `BrowserBox` и доступные действия без переноса управления процессами в renderer process.

## System Contracts

### Key Contracts

* Каждый бокс имеет уникальный идентификатор, отдельный `UserDataDir`, выбранный браузер и профиль сервера либо прямой сетевой выход.
* Запуск должен быть упорядочен: сначала запуск и проверка готовности per-box SOCKS5-прокси, затем запуск браузера с `--proxy-server` и `--user-data-dir`.
* У каждого бокса должен быть отдельный локальный proxy port. Порт необходимо резервировать до записи конфигурации, чтобы обнаружить конфликт до запуска процесса.
* Остановка и удаление должны завершать процессы бокса перед удалением его `UserDataDir`.
* Падение или завершение браузера не должно оставлять управляемый runtime бокса в состоянии «запущен».
* Fingerprint-подмена canvas, WebGL, шрифтов, часового пояса, языка и user-agent не входит в MVP и не должна подразумеваться базовой изоляцией.
* DNS-маршрутизация, WebRTC-защита и ограничения обхода прокси должны быть проверены отдельно до заявления о полной сетевой изоляции.

### Integration Contracts

* `BrowserBox` описывает идентификатор, имя, выбранный браузер, `serverProfileId`, `userDataDir`, `proxyPort`, цвет, время создания, время последнего запуска и заметки.
* `BrowserBoxManager` должен предоставлять операции создания, удаления, запуска, остановки, перечисления, получения и частичного обновления бокса через IPC.
* `BoxRuntime` должен принимать `ServerProfile` и возвращать состояние готовности, ошибки запуска и состояние завершения процессов.
* Renderer должен получать только данные состояния и результаты операций через preload bridge. Доступ к child processes и файловой системе должен оставаться в main process.
* При отсутствии выбранного профиля сервера runtime должен поддерживать прямой выход, если это разрешено согласованным решением о поведении.

## Architecture Decision Records

### ADR-001: Отдельный sing-box process на каждый бокс как целевое предложение

**Context:** План сравнивает общий sing-box с несколькими SOCKS5-inbounds и отдельный sing-box для каждого бокса. Общий процесс требует перезапуска и может погасить другие сессии при изменении бокса. Отдельные процессы требуют больше памяти и контроля завершения.

**Decision:** В качестве целевой архитектуры предложить отдельный sing-box process на каждый бокс, управляемый `BoxRuntime` через `Map<boxId, ChildProcess>`. Это предложение требует подтверждения до реализации.

**Consequences:** Боксы получают более независимый жизненный цикл и сбой одного процесса не обязан останавливать другие. Возникают расходы памяти, необходимость watchdog и отдельная обработка cleanup.

### ADR-002: Chromium user-data directory для изоляции данных

**Context:** MVP должен разделять cookies, localStorage, кэш и расширения между боксами.

**Decision:** Каждый бокс должен запускать выбранный Chromium-браузер с отдельным `UserDataDir`. Предлагаемый путь по умолчанию: `<userData>/boxes/<id>/profile`.

**Consequences:** Профили получают отдельное persistent-хранилище. Размер данных может достигать 100–500 MB на бокс и требует отображения и очистки кэша.

### ADR-003: MVP без fingerprint-подмены

**Context:** План включает fingerprint-изоляцию как отдельную последующую итерацию из-за CDP injection и связанных рисков.

**Decision:** Целевой MVP ограничивается IP-изоляцией через proxy endpoint и изоляцией browser storage. Изменение canvas, WebGL, шрифтов, часового пояса, языка и user-agent откладывается.

**Consequences:** Функция не должна обещать защиту от корреляции по fingerprint. Полная fingerprint-изоляция потребует отдельного решения и отдельного объёма работ.
