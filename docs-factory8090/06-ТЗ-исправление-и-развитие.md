## 1. Назначение и границы

Документ задаёт единый план доведения VPN Tunnel Enforcer до согласованного, проверяемого и сопровождаемого состояния. Он объединяет исправление подтверждённых дефектов, устранение расхождений документации, усиление безопасности, завершение заявленных функций и подготовку плановых функций.

Документ не закрывает продуктовые решения из `docs-factory8090/05-открытые-вопросы.md`. Эти вопросы остаются открытыми без изменения формулировок и перечислены в конце как блокеры или входные решения для соответствующих работ.

Исходное состояние:

- Windows Electron-приложение, package version `1.1.22`, Electron 42, sing-box + Wintun, Xray для отдельных REALITY-профилей.
- Основные границы: Electron main, preload/contextBridge, renderer, системные PowerShell/Windows API, дочерние runtime-процессы и установщик NSIS.
- В исследовании: 214 требований, 927 критериев приёмки, 185 аудиторских находок, 128 нумерованных открытых вопросов.
- Локальные незакоммиченные изменения пользователя не являются частью этого ТЗ и не должны включаться в работы автоматически.

## 2. Нормативные принципы

1. **Безопасность важнее доступности.** При невозможности доказать безопасный маршрут система блокирует или помечает состояние как «не проверено», но не сообщает об успехе.
2. **Одна модель состояния.** Подключение, автоматизация, диагностика и UI используют единый lifecycle coordinator и конечный автомат. «Переход» обозначает процесс между состояниями, а не состояние подключения.
3. **Доказуемость.** Любой результат проверки содержит источник, маршрут, время, ограничения и признак достоверности.
4. **Атомарность и обратимость.** Системные изменения и хранилища применяются через snapshot/manifest, temp+rename, журнал операции и идемпотентный rollback.
5. **Минимальная экспозиция секретов.** Секрет не покидает main без обоснованного контракта; логи, IPC-ошибки, экспорт и диагностика проходят redaction.
6. **Совместимость с фактическим runtime.** Конфигурация проверяется против реально поставляемых версий бинарников, а неподдержанный профиль отклоняется до изменения системы.
7. **Изменения наблюдаемы.** Каждая автоматическая операция имеет correlation id, владельца, причину, отмену и результат.
8. **Открытые вопросы не подменяются догадками.** До ответа владельца применяется только безопасный временный fallback, явно помеченный в UI и тестах.

## 3. Целевое состояние продукта

### 3.1 Подключение и lifecycle

Единый координатор управляет ручным подключением, остановкой, перезапуском, адаптивным обходом, расписанием, ротацией и AutoPilot. Допустимые стабильные состояния: `disconnected`, `connecting`, `connected`, `disconnecting`, `reconnecting`, `error`, `blocked`, `unknown`. Значения `connecting`, `disconnecting` и `reconnecting` являются переходами/операциями и не должны отображаться как устойчивое «подключено».

Для каждой операции обязательны: owner (`manual`, `schedule`, `rotation`, `autopilot`, `adaptive`, `recovery`, `installer`), operation id, generation, AbortSignal, deadline, progress, terminal result и безопасная отмена. Новая операция отменяет или ставится в очередь по политике, принятой владельцем; до решения открытых вопросов конфликт не должен приводить к глобальной остановке чужой активной операции.

Запуск выполняется в порядке: validate profile/runtime -> snapshot system state -> prepare runtime -> start upstream/Xray -> start sing-box -> verify TUN and protected route -> apply/verify kill-switch and adapter/DNS policy -> publish `connected`. Любой сбой выполняет согласованный rollback или сохраняет блокировку и выдаёт `blocked/unknown`, но не ложный `connected`.

Остановка выполняется в обратном порядке с ожиданием выхода процессов, закрытием listeners, подтверждением удаления TUN, откатом системных изменений и записью истории подключения.

### 3.2 Безопасность и системные изменения

- Секреты профилей и подписок шифруются через выбранный владельцем механизм Windows DPAPI/Electron `safeStorage`, с версионированной миграцией и аварийным отказом без потери старых данных.
- Runtime-каталог создаётся в доверенной директории, получает ACL до запуска elevated-процесса; ошибка ACL останавливает запуск.
- Владелец процесса определяется по нормализованному абсолютному пути с разделителем, PID, command line/config path и подписи/хэшу, где это возможно.
- Kill-switch, baseline, IPv6/DNS/adapter lockdown и browser hardening используют независимые manifest-снимки, контроль целостности, атомарную запись и частичный rollback с явным результатом каждого шага.
- Boot recovery от SYSTEM читает только подписанные/ACL-защищённые manifest-файлы из доверенной области, проверяет владельца и версию схемы.
- Исключения firewall валидируются по типу, существованию, canonical path, IP/CIDR, длине и дубликатам. Изменение активного исключения либо применяется сразу, либо явно помечается «будет применено при следующем запуске» согласно решению владельца.

### 3.3 Серверы, импорт и подписки

Импорт поддерживает заявленные URI, JSON/YAML, смешанный текст, Happ payloads и подписки без двойного декодирования, с корректным IPv6/SIP002, `happ://add`, `crypt3/4/5`, ECH и WireGuard-совместимостью только для фактической версии runtime. Профиль нормализуется без молчаливого удаления поддерживаемых полей; несовместимость показывается до запуска.

Обновление подписки выполняется транзакционно: fetch/decode/parse/validate -> diff -> persist через сериализованную очередь -> UI result. Сетевая ошибка возвращает `ok: false`, сохраняет предыдущие профили и не выдаёт пустой результат за успешный. Удалённые профили получают срок/политику хранения после ответа владельца, а секреты не остаются бессрочно в архиве без явного TTL.

Интервалы обновления нормализуются и показываются единым компонентом: провайдерский диапазон 15 минут–24 часа, ручной диапазон 1 минута–24 часа, default 30 минут при отсутствии валидного значения. Селектор частоты должен использовать тот же `MacSelect`/design tokens, размеры, отступы, радиусы, цвета, focus/disabled/error состояния и локализацию, что остальные настройки. Никаких отдельной стилистики или слова «переход» в label состояния подключения.

История live-проверок:

- хранится в `app.getPath('userData')/live-server-checks.json`;
- ключи: `profile:<id>`, `host:<host>`, `global`;
- максимум 20 результатов на цель, новые записи впереди;
- перед записью удаляются секреты и маскируются UUID;
- сравнение выполняется с последней успешной проверкой;
- UI должен показывать все рассчитанные изменения: IP, TLS fingerprint, ASN, страну, задержку, порты, handshake, egress IP, PMTU и скорость, а не только IP/TLS;
- UI получает явную очистку истории и подтверждает результат; повреждённый файл восстанавливается через backup, а не молча стирается.

### 3.4 Маршрутизация и DNS

Smart RU, доменные правила, split tunneling и DNS профили имеют детерминированный порядок и тесты конфликтов. Точное доменное правило не создаёт suffix-совпадение без явного выбора. Приоритет пользовательских override фиксируется в таблице правил. Rule-set принимается только после проверки ожидаемого checksum/signature и атомарной замены; при ошибке используется локальный проверенный fallback с диагностическим статусом.

### 3.5 Мониторинг, диагностика и форензика

Любая проверка различает `passed`, `failed`, `not-checked`, `indeterminate`. Отсутствие лога или внешнего источника не превращается в «утечек нет». Передача IP/ASN/геоданных внешним сервисам управляется единым privacy policy и отображается пользователю.

Диагностический ZIP формируется одним redactor-контекстом: прокси URL, токены, ключи, user/account paths, IP и системные идентификаторы маскируются по политике. Ошибка удаления staging не подавляется без регистрации и итогового `cleanupFailed`. Speed test, availability и leak check сохраняют несоответствие egress IP как неподтверждённый результат.

Форензика корректно останавливает ETW sidecar, ждёт flush/exit, закрывает trace session и проверяет границы `pktmon --pkt-size 0` с явным opt-in и предупреждением. UDP remote endpoint, reset/drop классификация и `dnsLeakDetected` имеют согласованную схему и тесты.

### 3.6 UI, IPC и локализация

- `contextBridge` остаётся единственной renderer-main границей.
- Все privileged IPC handlers проверяют senderFrame/origin, входные данные runtime-схемой и возвращают типизированный результат.
- `shared/ipc-types.ts`, preload и main содержат одинаковый список каналов; удаляются неэкспонированные/пропущенные декларации.
- Полный URI с секретом не возвращается renderer без явного подтверждения и одноразового минимального контракта.
- `sandbox` и CSP задаются явно одинаково для dev/prod с контролируемыми исключениями.
- Устраняются вложенные интерактивные элементы, таймеры после unmount, статический modal id, отсутствие focus trap/focus restore и `lang` drift.
- Все пользовательские строки проходят ru/en i18n; непереведённые русские строки считаются CI-ошибкой.
- Design system переименовывается или приводится к фактической Windows-визуальной системе; все селекторы частоты, статусы и модалки используют единый набор токенов.

### 3.7 Soft-режим и автоматизация

Soft Autoconfig применяет только поддержанные targets, хранит точный baseline каждого изменённого значения и откатывает только собственные изменения, не затирая последующие правки пользователя. IPv6 proxy addresses, `setx` length limit, Git/Gradle и актуальный Android Studio path покрываются тестами.

Scheduler работает с timezone-aware instant/zone rules, корректно обрабатывает DST, полночь и пересечения. Rotation меняет выбранный профиль только после успешного health/connect; при отказе остаётся рабочий профиль или безопасное отключённое состояние. AutoPilot, adaptive retry и ручные действия используют общего координатора.

### 3.8 Установщик и поставка

Установщик перед обновлением вызывает безопасный application shutdown с rollback, а не `taskkill` по имени образа. Бинарники имеют зафиксированные версии, SHA-256/подписи и проверку перед упаковкой/запуском. NSIS сохраняет пользовательские данные, очищает только заявленные артефакты, а хуки и комментарии соответствуют фактическому поведению.

Сборка должна быть воспроизводимой: `build:sidecar` и snapshot либо обязательны с диагностируемой ошибкой, либо явно маркируют fallback. Добавляется release manifest с версиями и hashes. Auto-update, поддержка Windows 10 и Electron upgrade выполняются только после решений владельца.

Плановые функции mihomo, AmneziaWG, process monitor и account boxes реализуются отдельными фазами через контракт адаптера, не смешиваются с исправлением текущего sing-box runtime и не включаются в production без лабораторных критериев.

Отдельно: F-173…F-180 относятся к рассогласованиям roadmap/документации и плановым функциям. Они не означают, что соответствующие будущие возможности уже должны быть включены в текущий production scope; это определяется WP-12 и открытыми вопросами.

## 5. Модель данных и миграции

1. Все persisted stores получают `schemaVersion`, migration id, checksum и backup-before-write.
2. Миграции выполняются в main, сериализованно, с dry-run summary и rollback. Старый формат удаляется только после успешной верификации нового.
3. Секреты мигрируются отдельно от публичных метаданных; при недоступном secure storage приложение не пишет plaintext fallback без явного безопасного режима.
4. Manifest системных изменений содержит owner, operation id, OS/build, schemaVersion, original values, applied values, hash и status каждого шага.
5. Live-check history записывается temp+rename с `.bak`; при повреждении выбирается backup и показывается warning.
6. История подключений, автоматизаций и диагностики ограничивается размером/возрастом только после ответов на соответствующие открытые вопросы; до этого сохраняется текущая политика и видимый лимит.

## 6. Тестовая стратегия и критерии приёмки

### 6.1 Обязательные уровни

- Unit/property tests для parser, validation, normalization, state machine, diff, redaction и migration.
- Main/preload contract tests для всех IPC channels и event unsubscribe.
- Renderer tests для state/status wording, keyboard, focus, error/empty/not-checked states и локализации.
- Integration tests с mocked processes/filesystem/network.
- Windows E2E для firewall, DNS, adapters, scheduled task, ACL, installer and recovery.
- Release smoke: `npm run typecheck`, `npm test`, `npm run build`, `npm run dist:win`, artifact inventory/hash/signature.

### 6.2 Запреты на приёмку

Релиз не принимается, если есть plaintext secret in logs/export, false-positive leak success, unowned process kill, non-atomic system rollback, unvalidated privileged IPC, corrupted-history data loss, unresolved TypeScript errors или undocumented behavior change.

### 6.3 Минимальные измеримые цели

Целевые значения из раздела «Success Metrics» остаются на согласование. До их утверждения CI обязан измерять и публиковать: тестовые counts, typecheck result, parser corpus coverage, migration result, IPC contract coverage, installer artifact hash, Windows E2E matrix and leak-check verdict distribution.

## 7. Порядок реализации

1. WP-0 и WP-1: контракты, секреты, IPC, безопасные ошибки.
2. WP-2 и WP-3: процессы, lifecycle, firewall, baseline и recovery.
3. WP-4 и WP-5: импорт, подписки, live checks and history.
4. WP-6 и WP-7: routing, DNS, leak/availability/speed/monitoring.
5. WP-8 и WP-9: diagnostics, forensics, Soft/browser/UI.
6. WP-10: automation/adaptive coordination.
7. WP-11: installer/release hardening.
8. WP-12: planned capabilities after compatibility gates.

Каждый пакет поставляется отдельным небольшим PR/commit с миграцией, тестами, обновлением blueprint/requirements и записью фактического результата. Нельзя закрывать находку только изменением текста документа.

## 8. Трассировка требований

Все 44 feature-документа остаются нормативным источником пользовательских требований и AC. WP-0…WP-12 являются планом реализации и должны ссылаться на конкретные `REQ-*`, `AC-*` и `F-*` в PR. Никакой критерий приёмки не считается выполненным без теста или проверяемого Windows E2E-доказательства.

Группы требований покрываются так:

- `REQ-CONN-*`, `REQ-LEAK-*`: WP-0…WP-3, WP-9, WP-10.
- `REQ-SRV-*`: WP-4…WP-6.
- `REQ-ROUTE-*`: WP-6…WP-7.
- `REQ-MON-*`, `REQ-DIAG-*`: WP-5, WP-7, WP-8.
- `REQ-SOFT-*`: WP-9.
- `REQ-AUTO-*`: WP-10.
- `REQ-SET-*`: WP-1, WP-9, WP-11.
- `REQ-ISO-*`, mihomo, AmneziaWG и process-monitor планы: WP-12 после решений владельца.

## 9. Реестр открытых вопросов

Открытые вопросы **не изменены и не закрыты**. Полный исходный реестр находится в `docs-factory8090/05-открытые-вопросы.md` (128 нумерованных пунктов). Ниже только указатели, чтобы перед началом соответствующего WP запросить у владельца нужные решения:

- Метрики, Windows 10, подписи/checksum/auto-update: разделы `Success Metrics`, `Technical Requirements`.
- Секреты, IPC origin/runtime validation, экспорт URI, manifest authority: разделы `Серверы и подписки`, `IPC-контракт`, `Хранилище`, `Системные изменения`.
- Kill-switch default и missing manifest, browser policy, DNS/geo privacy: разделы `Защита от утечек`, `Kill-switch`, `Защита браузеров`, `Мониторинг`.
- Scheduler/rotation/AutoPilot/adaptive priority, stealthMode, fingerprint: разделы `Автоматизация`, `Расписание`, `AutoPilot`, `Адаптивный обход блокировок`.
- Protocol/runtime targets WireGuard, mihomo, AmneziaWG, Android Studio, diag: соответствующие feature-разделы.
- История подключений, сроки хранения, внешний IP privacy и критерии leak/availability/speed: разделы `История`, `IP и трафик`, `Проверка утечек`, `Проверка доступности`, `Тест скорости`.
- Account boxes and process monitor: плановые разделы `Изоляция аккаунтов` и `Процессный монитор`.

## 11. Definition of Done

Работа считается завершённой только если:

1. Код, тесты, миграции и документация согласованы.
2. Все затронутые `REQ-*`, `AC-*` и `F-*` имеют ссылку на реализацию и доказательство.
3. Нет plaintext secrets, ложных success verdicts и необратимых системных изменений без manifest.
4. Ручные и автоматические операции используют единый lifecycle coordinator.
5. Windows E2E и installer smoke прошли на поддерживаемой матрице.
6. `npm run typecheck`, `npm test`, `npm run build` и `npm run dist:win` завершились успешно; результаты и хэши артефактов записаны.
7. Все нерешённые вопросы перечислены в `05-открытые-вопросы.md` и не представлены как закрытые.
