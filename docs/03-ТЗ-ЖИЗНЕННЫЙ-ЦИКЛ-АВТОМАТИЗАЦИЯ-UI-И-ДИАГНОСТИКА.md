## 1. Единый координатор жизненного цикла и конечный автомат (Lifecycle Coordinator)

### 1.1 Модель состояний туннеля (State Machine; WP-0)
Система управляется строго детерминированным конечным автоматом, исключающим рассинхронизацию между фоновыми процессами и пользовательским интерфейсом:

```
                      ┌─────────────────────────┐
                      │      DISCONNECTED       │◄───────────────────────┐
                      └────────────┬────────────┘                        │
                                   │ start()                             │
                                   ▼                                     │
                      ┌─────────────────────────┐                        │
                      │       CONNECTING        │ (Переходная операция)  │
                      └────────────┬────────────┘                        │
                                   │                                     │
                      ┌────────────┴────────────┐                        │
       Успех проверки │                         │ Ошибка / Abort         │
                      ▼                         ▼                        │
         ┌─────────────────────────┐   ┌─────────────────────────┐       │
         │        CONNECTED        │   │          ERROR          │───────┤
         └────────────┬────────────┘   └─────────────────────────┘       │
                      │                                                  │
       Переподключение│                 Сбой сети / Handshake lost       │
                      ├─────────────────────────┐                        │
                      │                         │                        │
                      ▼                         ▼                        │
         ┌─────────────────────────┐   ┌─────────────────────────┐       │
         │      RECONNECTING       │   │         BLOCKED         │       │
         │  (Переходная операция)  │   │  (Сработал Kill-Switch) │       │
         └────────────┬────────────┘   └────────────┬────────────┘       │
                      │                             │                    │
                      │ stop()                      │ Emergency Rollback │
                      ▼                             ▼                    │
         ┌─────────────────────────┐   ┌─────────────────────────┐       │
         │      DISCONNECTING      │   │         UNKNOWN         │       │
         │  (Переходная операция)  │   │   (Повреждён манифест)  │───────┘
         └────────────┬────────────┘   └─────────────────────────┘
                      │
                      └────────────────────────►─────────────────────────┘
```

1. **Допустимые стабильные состояния конечного автомата (TunnelState):** `disconnected`, `connected`, `error`, `blocked`, `unknown`.
2. **Переходные операции:** `connecting`, `disconnecting`, `reconnecting`.
   - **Нормативное требование отображения:** Запрещено отображать переходные операции как стабильное состояние «Подключено». Слово «переход» в label статуса не допускается; UI отображает анимированный спиннер и статус: *«Установка защищённого соединения...»* или *«Отключение...»*.
3. **Операционные субстатусы и состояния дочерних процессов:**
   - **Здоровье соединения (`health: 'ok' | 'degraded'`):** Субсостояние `degraded` выставляется внутри стабильного состояния `connected` при обнаружении расхождения DNS (possible DNS leak), частичной потери пакетов или недоступности валидации полного туннеля (F-199).
   - **Статус локального прокси (`proxyStatus: 'running' | 'proxy-down' | 'stopped'`):** Субстатус `proxy-down` эмитируется сторожевым таймером (watchdog) при сбое локального SOCKS-прокси (3 подряд неудачных TCP-пробы) без разрыва системного TUN-адаптера для инициации быстрого failover.
   - **Жизненный цикл процессов (`processState: 'running' | 'stopped'`):** Термин `running` относится строго к статусу управляемого процесса ОС в реестре супервизора `ManagedChildProcess` (sing-box, Xray, ETW-сайдкар) и не подменяет собой состояние туннеля в IPC `tunnel:get-status`.
4. **Обработка необработанных сбоев main-процесса (Решение: Блоки 1–2, Вариант C; WP-2; F-131):**
   - Перехватчики `uncaughtException` и `unhandledRejection`:
     - **Если туннель был активен:** Выполняется немедленный контролируемый rollback сетевых изменений (сброс firewall, адаптеров, DNS) и перевод статуса автомата в `unknown` (с фиксацией кода сбоя `crashRollback`) и уведомлением пользователя. Операционный субстатус `degraded` относится исключительно к состоянию `connected` и в статусе `unknown` не используется.
     - **Если туннель был неактивен:** Выполняется запись инцидента в лог с обеспечением отказоустойчивости приложения без вмешательства в системные сетевые адаптеры.
5. **Контроль статуса конкурирующих интерфейсов и сохранение состояний сбоя (F-195):**
   - Детектор конкурирующих интерфейсов (`competingTunDetector`) не имеет права самостоятельно вызывать `emitStatus('running')` или перезаписывать состояния сетевых ошибок (`error`, `proxy-down`, `blocked`, `unknown`).
   - Устранение конкурирующего адаптера лишь снимает блокировку конфликта; итоговое состояние туннеля вычисляет исключительно единый координатор жизненного цикла (`Lifecycle Coordinator`) с учётом фактического состояния дочернего процесса прокси-ядра.

### 1.2 Приоритеты операций и координация (Решение: Блоки 1–2, Вариант A; WP-0, WP-10; F-125, F-128, F-133)
Для предотвращения race conditions между пользователем и фоновой автоматизацией установлена **жесткая иерархия блокировок**:

$$\text{Recovery} > \text{Manual (Пользователь)} > \text{Schedule (Расписание)} > \text{Rotation (Ротация)} > \text{AutoPilot} > \text{Adaptive Retry}$$

1. **Приоритет ручного действия (Блок 1–2, Вариант A; F-125):**
   - Ручное действие пользователя (клик «Подключить» / «Отключить» / смена профиля) немедленно прерывает любую фоновую автоматическую операцию через `AbortController.abort()`.
2. **Метаданные операции (WP-0; F-133):**
   - Каждая операция получает уникальный `operationId` (UUID v4), метку времени, владельца (`owner`), ссылку на `AbortSignal` и таймаут (deadline). Поздние асинхронные callbacks от предыдущих отменённых операций игнорируются.

### 1.3 Централизованный супервизор дочерних процессов и системные ресурсы (WP-2; F-003, F-012, F-018, F-110, F-134, F-135, F-136, F-137)
1. **Единый реестр процессов:**
   - Процессы `sing-box.exe`, `xray.exe`, `amneziawg-go.exe`, `traffic-forensics-sidecar.exe` регистрируются в менеджере `ManagedChildProcess`.
   - Проверка пути выполняется со строгим разделителем: `ExecutablePath.StartsWith($runtimeDir + "\")` (F-003).
2. **Двухэтапная остановка (F-110):**
   - Отправка сигнала штатного завершения (SIGTERM/Ctrl+C) с таймаутом ожидания 1.5 секунды. При отсутствии завершения — немедленный `taskkill /F /PID`.
3. **Корректный статус туннеля (F-012):**
   - Реальный PID активного ядра транслируется в статус подключения и доступен в IPC `tunnel:get-status`.
4. **Гарантированная очистка Tray при выходе (F-134):**
   - При завершении приложения объект системного трея `Tray` явно уничтожается вызовом `.destroy()`, исключая появление «фантомных» иконок в панели задач Windows.
5. **Безопасная загрузка системных снимков (F-135):**
   - Загрузчик `snapshotLoader` исключает состояние гонки при быстром перезапуске приложения.
6. **Очистка слушателей nativeTheme (F-136):**
   - Модуль `themeManager` гарантированно удаляет слушатель `nativeTheme.on('updated')` при размонтировании и завершении работы.
7. **Конфигурация окна приложения (F-137):**
   - Устранено противоречие конфигурации окна: обеспечена полная согласованность между режимами `frame: true` и кастомным titlebar.

## 2. Подсистемы автоматизации сети

### 2.1 Планировщик расписания (Scheduler; Решение: Блоки 1–2, Вариант A; WP-10; F-122, F-123, F-193)
1. **Учет часовых поясов, переходов времени и ночных окон (F-122, F-193):**
   - Расписание оперирует объектами времени с привязкой к локальному часовому поясу системы через `Intl.DateTimeFormat` с поддержкой сезонного перевода часов (DST).
   - **Устранение бага перехода через полночь (F-193):** Для окон, пересекающих полночь (например, с 23:00 до 07:00), алгоритм обязан проверять оба диапазона активности: попадание текущего времени в отрезок с `start` до 23:59:59 текущих суток, а также отрезок с 00:00:00 до `end` с учетом активности предыдущего дня (`dayOffset = -1`). Исключено ложное отключение защиты в утренние часы после полуночи.
2. **Объединение пересекающихся расписаний (Блок 1–2, Вариант A; F-123):**
   - Если активны несколько расписаний, интервалы которых перекрываются, система объединяет их в **единое активное защитное окно**.
   - Наступление времени окончания одного из расписаний **не выключает туннель**, если в этот момент действует второе активное расписание. Отключение происходит только при закрытии всех окон.

### 2.2 Ротация серверов (Server Rotation; Решение: Блоки 1–2, Вариант A; WP-10; F-124, F-128)
1. **Принцип «Health-Before-Commit» (Блок 1–2, Вариант A; F-124):**
   - При наступлении интервала ротации ядро инициирует проверку здоровья следующего по очереди профиля.
   - Если переподключение на новый сервер завершилось неудачей, **система немедленно возвращает предыдущий рабочий сервер**.
   - Переключение активного профиля в конфигурации фиксируется только после успешного прохождения проверки доступности (handshake probe) нового узла.
2. **Упорядочение очереди смены конфигурации (F-128):**
   - Запросы на обновление настроек ротации из UI проходят через сериализованную очередь с дедупликацией идентификаторов профилей.

### 2.3 Адаптивный обход блокировок (Adaptive Censorship Bypass; WP-10; F-126, F-127)
1. **Многоуровневая цепочка адаптации (Adaptive Fallback Chain):**
   При фиксации блокировки текущего протокола (сбросы TCP RST, тайм-ауты, TSP DPI) координатор автоматически перебирает стратегии обхода:
   $$\text{Direct (Базовый VLESS)} \longrightarrow \text{Reality (TLS Camouflage)} \longrightarrow \text{Hysteria 2 (UDP/QUIC)} \longrightarrow \text{Shadowsocks} \longrightarrow \text{[Целевой этап WP-12: AmneziaWG]}$$
   *(Примечание: поддержка протокола AmneziaWG в цепочке обхода реализуется в рамках целевого пакета WP-12 при внедрении сателлита amneziawg-go).*
2. **Окно стабильности (Stability Window; F-127):**
   - Выученный режим обхода фиксируется только после **20-секундного проверочного окна**, в котором узел обязан успешно ответить минимум на **2 из 3 проверочных проб**.
3. **Расширенный отпечаток профиля (Profile Fingerprint; F-126):**
   - Хэш отпечатка профиля формируется с учётом: типа транспорта (TCP, WS, gRPC), параметров Reality (`pbk`, `sni`), параметров обфускации, типа клиентского устройства и TLS/uTLS фингерпринта. Выученный режим обхода никогда не экстраполируется на профили другой архитектуры.
4. **Миграция legacy `stealthMode`:**
   - Старый бинарный флаг `stealthMode` прозрачно мигрирует в адаптивный режим, сохраняя обратную совместимость.

### 2.4 Автоматическая настройка приложений (Soft-режим; WP-9; F-014, F-117…F-121)
1. **Android Studio (Решение: ТЗ 3.7; WP-9; F-118, F-119, F-120):**
   - Поддержан актуальный конфигурационный файл `options/proxy.settings.xml` современных версий IDE вместо устаревшего `options/other.xml`.
   - Значения хоста экранируются по стандарту XML (`&amp;`, `&quot;`, `&lt;`, `&gt;`).
   - При откате удаляются только внесённые приложению XML-теги, сохраняя остальные пользовательские параметры блока `HttpConfigurable`.
2. **Git и Gradle (WP-9; F-121):**
   - Перед внесением изменений формируется точный снимок изменяемых ключей. При откате восстанавливаются только затронутые ключи, не затирая правки, сделанные пользователем во время сессии.
3. **Системные переменные окружения (WP-9; F-014, F-117):**
   - Применение переменных среды через PowerShell напрямую в реестр Windows (`HKCU\Environment`), минуя утилиту `setx.exe`, обходя ограничение длины в 1024 символа.
   - Корректный разбор IPv6-адресов прокси в квадратных скобках `[::1]:10808`.

## 3. Серверы, подписки и история live-проверок

### 3.1 Конвейер импорта и декодирования ключей (Решение: Блок 4; WP-4; F-045…F-051, F-057, F-058)
1. **Устранение двойного декодирования (F-045):**
   - Исключено повторное применение `safeDecode()` после вызова `URLSearchParams.get()`. Пароли, SNI и пути, содержащие литеральный символ `%`, сохраняются без повреждений.
2. **Декодирование SIP002 Shadowsocks (F-046):**
   - Authority-часть URI декодируется до вызова `splitHostPort()`, гарантируя корректное извлечение IPv6-хостов и нестандартных учетных записей.
3. **Поддержка форматов Happ (Решение: Блок 4, Вариант A; F-048, F-049):**
   - Полная поддержка разбора `happ://crypt4/*` (современный формат) и `happ://add/<base64-json>` с извлечением поля `url`.
4. **Валидация Base64 и Markdown (F-057, F-058):**
   - Проверка каноничности base64-кодирования (round-trip check). Очистка завершающей пунктуации при копировании URI из Markdown-текстов.
5. **Сохранение uTLS и ALPN с предупреждением (Решение: Блок 4, Вариант B; F-051):**
   - При импорте пользовательские параметры uTLS и ALPN сохраняются, а в UI выводится информационное уведомление о выбранном профиле маскировки.

### 3.2 Управление подписками и архив ключей (Решение: Блок 4; WP-4; F-063, F-064, F-069, F-070, F-179)
1. **Сериализованная очередь транзакций (Блок 4, Вариант A; F-063, F-070):**
   - Все операции записи в массив профилей (импорт, обновление подписки, ручное редактирование, health check) выполняются через последовательный асинхронный мьютекс. Параллельные гонки типа read-modify-write исключены.
2. **Явная обработка сетевых ошибок подписки (Блок 4, Вариант A; F-064):**
   - При сбое обновления подписки метод `refreshGroup()` возвращает `{ ok: false, error: ... }`. Предыдущие рабочие профили группы сохраняются в неизменном виде. UI отображает ошибку обновления.
3. **Архив удалённых ключей (Блок 4, Вариант A; F-069):**
   - Ключи, пропавшие из подписки при обновлении, перемещаются в архив с **TTL 30 дней**.
   - По истечении 30 дней архивные ключи безвозвратно удаляются автоматическим фоновым сборщиком. Срок хранения отображается в UI.
4. **Интервалы обновления подписок (F-179):**
   - Нормализованный диапазон: от 15 минут до 24 часов (по умолчанию 30 минут). Ручное обновление доступно с интервалом от 1 минуты.

### 3.3 История проверок серверов и трафика (Решение: Блок 6, Вариант A; WP-5; F-068, F-071, F-181, F-185)
1. **Хранение и атомарная запись (WP-5; F-071):**
   - История live-проверок сохраняется в `app.getPath('userData')/live-server-checks.json`.
   - Запись выполняется по схеме `temp+rename` с формированием резервной копии `.bak`.
   - Лимит: не более 20 записей на цель (`profile:<id>`, `host:<host>`, `global`).
2. **Отображение полного диффа (Блок 6, Вариант A; WP-5; F-185):**
   - Пользовательский интерфейс отображает сравнение с последней успешной проверкой по всем **10 параметрам**:
     1. IP-адрес узла
     2. Отпечаток TLS (JA3/JA4 / TLS fingerprint)
     3. Номер автономной системы (ASN)
     4. Страна и город
     5. Задержка (Latency RTT)
     6. Доступность портов
     7. Время рукопожатия (Handshake duration)
     8. Реальный выходной IP (Egress IP)
     9. Path MTU (PMTU)
     10. Скорость загрузки
3. **Корректная обработка TLS Probe (F-068):**
   - При выполнении TLS probe использование флага `rejectUnauthorized: false` сопровождается явной отметкой о недоверенном сертификате, исключая ложный статус `status: ok` без предупреждения.
4. **Действия в интерфейсе и объединение истории (WP-5; F-181, F-185):**
   - В UI добавлены кнопки **«Очистить историю проверок»** и **«Экспорт истории (JSON/CSV)»**.
   - История подключений полностью интегрирована в экран истории трафика, устраняя рассогласование между хранилищем и UI (F-181).

## 4. Мониторинг, диагностика и форензика трафика (ETW Sidecar)

### 4.1 Мониторинг соединений и трафика (WP-7; F-081, F-082, F-083, F-089, F-156)
1. **Точность счетчиков и времени (F-081, F-082):**
   - Байтовые счётчики интерфейса обрабатываются с точностью 64-битных целых чисел (`BigInt`), исключая переполнение на объемах трафика свыше 4 ГБ.
   - Временные метки парсятся с сохранением локального смещения часового пояса (например, `+0300`), исключая искусственную подмену на UTC `Z`.
2. **Сэмплер Clash API (F-083, F-089):**
   - Привязка трафика выполняется по составному ключу `(connection.id, connection.metadata.destinationIP, connection.metadata.destinationPort)`, исключая наложение трафика при переиспользовании ID.
3. **Оптимизация опроса в фоновом режиме (F-156):**
   - При сворачивании окна или неактивной вкладке (`document.hidden === true`) частота опроса статистики снижается с 1 раза в секунду до 1 раза в 10 секунд, экономя заряд батареи и CPU.

### 4.2 Проверка доступности URL и самопроверка утечек (Решение: Блок 6; WP-7; F-073, F-080, F-084, F-085, F-087, F-090, F-092…F-095)
1. **Нормализация адресов (Блок 6, Вариант A; F-080):**
   - Ввод URL без указания схемы (например, `youtube.com`) автоматически нормализуется в `https://youtube.com` на всех этапах обработки.
2. **Семантика статусов доступности (Блок 6, Вариант A; F-084, F-085, F-090, F-094):**
   - Успешный TCP/TLS-пинг **не фабрикует статус HTTP 200**. Задержка TCP фиксируется отдельно от HTTP-ответа (F-084).
   - Ответы HTTP 401 и 403 классифицируются как *«Требует авторизации (доступность не подтверждена)»* (F-085).
   - Twitch HLS probe использует запрос GET плейлиста/манифеста вместо искажённого HEAD, предотвращая ошибки CDN-кэширования (F-090).
   - При проверке пинга через Windows CLI учитывается факт, что утилита `ping.exe` возвращает `exitCode 0` даже при наличии частичной потери пакетов; парсер проверяет фактическое поле `Lost = 0` (F-094).
3. **Классификация утечек DNS и WebRTC (Блок 6, Вариант A; F-087, F-092, F-100):**
   - При расхождении между DNS-сигналом и шлюзом туннеля выставляется статус **`possibleDnsLeak`** с раскрытием всех деталей расхождения в UI. Флаг `dnsLeakDetected` устанавливается в `true`.
   - Встроенная самопроверка утечек через STUN-серверы тестирует WebRTC на утечку реального IP (F-087).
4. **Обработка отсутствия лога sing-box (Блок 6, Вариант A; F-093):**
   - Если журнал ядра недоступен для анализа direct-out, система рапортует честный статус **`notChecked` («Не проверено»)** с указанием причины. Вывод ложного вердикта «Утечек нет» строго запрещён.
5. **Внешние гео-сервисы (Решение: Блоки 1–2, Вариант A; F-072, F-073, F-086, F-088):**
   - Запросы к `ipapi.co`, `ipwho.is` и `geojs.io` (устранено расхождение документации F-073) разрешены по умолчанию с обязательным rate limiting, экспоненциальным backoff при HTTP 429 и скрытием публичных IP в debug-журналах.

### 4.3 Тест скорости (Решение: Блок 6; WP-7; F-010, F-096)
1. **Несовпадение выходного IP (Блок 6, Вариант B; F-010):**
   - Если egress IP во время теста скорости отличается от ожидаемого адреса туннеля, пользователю выводится предупреждение, однако результат замера скорости засчитывается и сохраняется в истории.
2. **Серверы замера скорости (Блок 6, Вариант A и B; F-096):**
   - Основные серверы тестируются по протоколу HTTPS. Использование HTTP-серверов допускается только в качестве запасного варианта с выводом предупреждения.

### 4.4 Экспорт диагностики (Решение: Блок 7; WP-8; F-004, F-097, F-178)
1. **Состав ZIP-архива (Блок 7, Вариант B):**
   - Технический состав архива (журналы, системные конфигурации, маршруты) сохраняется в полном объёме, но проходит обязательную финальную очистку единым сервисом `RedactionService`.
2. **Очистка staging-папки (Блок 7, Вариант A; F-178):**
   - Ошибка удаления временной папки выгрузки не подавляется, а транслируется в статус операции и UI-предупреждение.

### 4.5 Форензика трафика и ETW-сайдкар (Решение: Блок 7, Блок 13; WP-8, WP-12; F-015, F-089, F-098…F-103, F-106…F-108, F-168, F-170…F-172, F-176, F-197, F-198)
1. **Режим работы и нагрузка (Блок 13, Вариант B):**
   - Постоянный фоновый мониторинг сетевых сокетов во время активной VPN-сессии с оптимизацией потребления CPU (< 0.5%).
2. **Адаптивная динамическая буферизация (Блок 13):**
   - **200–300 мс** — при открытой вкладке мониторинга в интерфейсе.
   - **1000–1500 мс** — при работе приложения в фоновом режиме.
   - **2–3 секунды (low-power)** — при сворачивании в трей или работе ноутбука от аккумулятора.
3. **Хранилище метрик (Блок 13):**
   - Локальная база SQLite/NDJSON ограничена размером **50 МБ** или глубиной **24 часа** с автоматической кольцевой ротацией (FIFO).
4. **Гибридный сбор через ETW Sidecar (Блок 13; WP-12; F-089, F-102):**
   - Связка провайдера ETW `Microsoft-Windows-TCPIP` (отслеживание Transmission Control Block — TCB) и WinsockAFD с системным снимком `GetExtendedTcpTable` (сопоставление по 4-tuple: src IP, src port, dst IP, dst port) обеспечивает 100% точность атрибуции трафика по PID процессов без сторонних драйверов ядра.
   - В Rust-компоненте сайдкара реализован корректный парсинг 16-байтового IPv6-блока `sockaddr_in6` (F-102).
5. **Стабильность сайдкара и совместимость `ferrisetw` (F-106, F-107, F-108, F-168):**
   - Устранены риски аварийной остановки (`panic = "abort"`): вызовы `.unwrap()` на мьютексах заменены на безопасную обработку ошибок; обновлены зависимости библиотеки `ferrisetw` (F-107, F-108).
   - Сборка Rust-сайдкара через `cargo build --release` интегрирована в CI-конвейер сборки проекта (F-168).
   - Выполнен чеклист готовности Фазы 4 Roadmap (F-106).
6. **Классификация вердиктов парсера (F-099, F-101):**
   - Селектор классифицирует события сетевых сбросов как `timeoutOrPacketLossLikely` при отсутствии прямого подтверждения закрытия сокета (F-099).
   - Обработаны случаи, когда поля `remoteAddress` и `remotePort` в UDP-событиях имеют значение `null` (F-101).
7. **Захват пакетов pktmon (Блок 7, Вариант B; F-103):**
   - Запуск `pktmon --pkt-size 0` производится при старте сессии глубокой форензики только с обязательным явным предупреждением пользователя о возможности сохранения незашифрованных данных.
8. **Остановка ETW-сайдкара (Блок 7, Вариант A; F-015):**
   - Штатное завершение с ожиданием сброса буферов (flush) до 5 секунд, после чего следует принудительный kill.
9. **Удаление каталога `diag/` (Решение: Блок 8, Вариант B; F-170, F-171, F-172):**
   - Устаревший диагностический стенд `diag/` подлежит обязательному удалению из репозитория как мёртвый код в рамках работ WP-8.
10. **Потоковый разбор журналов форензики и защита от OOM (F-197):**
    - Загрузку файла `events.ndjson` сессии захвата трафика (объемом до 50 МБ и выше) запрещено выполнять через единовременное вычитывание в память `fs.promises.readFile()`.
    - Обработка, фильтрация и агрегация событий форензики реализуются через потоковый построчный разбор (`readline` / chunked stream) с настраиваемым лимитом результирующей выборки, исключая исчерпание памяти (OOM) процесса Node.js / Electron.
11. **Предотвращение ложного закрытия сессии захвата (F-198):**
    - Проверка наличия артефактов завершения сессии (`hasStopArtifacts`) обязана синхронизироваться с реальным жизненным циклом процесса захвата через PID Supervisor.
    - Обнаружение промежуточных файлов остановки не должно переводить сессию в статус `stopped`, пока фоновый процесс захвата пакетов фактически активен и удерживает открытые дескрипторы.

## 6. Метрики успеха продукта (Решение: Блок 6, Вариант C)

В соответствии с решением владельца продукта (Блок 6, Вариант C) целевые пороговые значения метрик фиксируются на этапе промышленной эксплуатации, однако **сбор локальных событий и счётчиков реализован в коде в полном объёме без использования внешней телеметрии**:

| Метрика | Способ локального расчёта | Событие в журнале аудита |
|---|---|---|
| **Отсутствие утечек (Leak-Free Rate)** | Доля сессий туннеля, в которых фоновая самопроверка не выявила пакетов через физический адаптер и DNS-расхождений. | `AUDIT_LEAK_CHECK_PASSED` / `AUDIT_LEAK_DETECTED` |
| **Время восстановления (MTTR)** | Время в миллисекундах от фиксации сбоя ядра до восстановления защищённого состояния туннеля. | `AUDIT_TUNNEL_RECOVERED` (длительность в мс) |
| **Успешность подключения** | Процент попыток запуска туннеля, завершившихся стабильным состоянием `connected`. | `AUDIT_CONNECTION_ATTEMPT` (результат: success/failure) |
| **Чистота отката системы** | Процент сессий завершения туннеля, после которых верификатор не обнаружил оставшихся правил firewall и измененных DNS. | `AUDIT_ROLLBACK_VERIFIED` (clean: true/false) |
| **Медианное время старта** | Медианная длительность фаз запуска туннеля от нажатия кнопки до подтверждения маршрутизации. | `AUDIT_STARTUP_PHASES` (замеры таймингов по фазам) |

- **Покрывает находки:** F-089, F-098, F-099, F-101, F-102, F-106, F-107, F-108, F-176, Traffic Observability RFC.
- **Содержание работ:** Постоянный фоновый мониторинг сокетов (< 0.5% CPU); адаптивная буферизация 200–300 мс / 1–1.5 с / 2–3 с; локальная база 50 МБ / 24 ч с ротацией FIFO; гибридная атрибуция через `Microsoft-Windows-TCPIP` + WinsockAFD + `GetExtendedTcpTable`.

## 8. Критерии приёмки и комплексный Definition of Done тома

### 8.1 Definition of Done (DoD)
1. **Кодовая согласованность:** Все модули `src/main`, `src/preload`, `src/renderer` проходят строгую проверку типов `npm run typecheck` без использования `any` на границах IPC.
2. **Тестовое покрытие:** Полный набор unit-, integration- и contract-тестов (`npm test`) завершается со 100% успехом.
3. **Безопасность данных:** Автоматический сканер секретов подтверждает отсутствие открытых ключей в журналах, снимках реестра и архивах экспорта.
4. **Сквозная проверка Windows E2E:** 
   - Проверено создание и удаление адаптеров Wintun (`VPNTE-TUN`, `awg-tun`).
   - Проверена изоляция Chromium Browser Boxes на версиях Chrome, Edge, Brave.
   - Проверена устойчивость к сбоям: симуляция падения процессов ядра и аварийной перезагрузки.
5. **Целостность сборки:** Сборка инсталлятора `npm run dist:win` формирует валидные артефакты с публикацией контрольных сумм в `checksums.txt`.

## 9. Срез реализации требований (2026-10-04)

Это приложение фиксирует состояние реализации и не меняет нормативные требования выше. «Выполнено» означает наличие кода и относящихся к нему автоматических проверок; это не заменяет Windows/L3-приёмку. «Частично» перечисляет выполненную часть и оставшуюся проверку или работу. «План WP-12» означает, что функция намеренно не допущена в production.
