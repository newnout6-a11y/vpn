# Методология приёмочного тестирования VPN Tunnel Enforcer

**Версия:** 1.0
**Дата:** 2026-09-28
**Область:** все рабочие пакеты WP-0…WP-12, все 927 критериев приёмки (AC), все находки аудита F-001…F-210.
**Назначение:** превратить критерии приёмки из документов требований и томов ТЗ в исполняемую, проверяемую и сопровождаемую систему тестов.

---

## 1. Принципы

1. **Тест без оракула — не тест.** Каждый тест имеет измеримый критерий PASS. Запрещённые формулировки: «не упало», «работает корректно», «отображается правильно». Только измеримое: «0 пакетов вне туннеля за окно 60 с по данным pktmon», «settings.json не содержит значения UUID профиля», «вердикт `indeterminate`, событие с correlation id присутствует в audit log».
2. **Вердикты зеркалируют продукт.** Результат теста: `PASS` / `FAIL` / `NOT-CHECKED` (среда не позволила выполнить проверку) / `INDETERMINATE` (сигналы противоречат друг другу). `NOT-CHECKED` не засчитывается как успех в релизном гейте — как и в продукте, отсутствие доказательства не является доказательством отсутствия дефекта.
3. **Безопасность важнее доступности.** Для каждого защитного свойства (kill-switch, шифрование секретов, IPC-граница, rollback) обязателен минимум один негативный/abuse-тест в дополнение к позитивному.
4. **Двойной оракул для критических инвариантов.** Каждый инвариант безопасности проверяется двумя независимыми методами. Пример для отсутствия утечек: внутренний оракул (счётчики WFP-фильтров, состояние манифеста) + внешний оракул (захват pktmon/Wireshark на физическом адаптере, внешний leak-сервис).
5. **Воспроизводимость.** Фиксированные фикстуры, seeded randomness для property-based тестов, зафиксированные версии ОС/ядер/зависимостей в протоколе прогона.
6. **Тест — тоже код.** Тесты ревьюятся, версионируются и удаляются по тем же правилам, что исходный код. Мёртвый тест хуже отсутствующего.

## 2. Схема идентификаторов и трассировка

- Формат: `AT-<WP>-<NNN>[.<вариант>]`, где `<WP>` — двузначный номер рабочего пакета (`03` = WP-3), `<NNN>` — порядковый номер в пакете, `.N` — вариант одной проверки на матрице сред.
  Пример: `AT-03-007.2` — тест 7 пакета WP-3, вариант на Windows 10 22H2.
- Каждый тест обязан содержать строку **Трассировка** со ссылками на `AC-*`, `REQ-*`, `F-*`, `WP-*`. Тест без трассировки отклоняется на ревью.
- Машиночитаемый инвентарь всех 927 критериев: `traceability/ac-inventory.csv` (генерируется скриптом из `docs-factory8090/02-фичи/**/requirements.md`).
- **Правило покрытия:** каждый AC из инвентаря покрывается минимум одним AT; каждая подтверждённая находка F — минимум одним регрессионным AT. Покрытие считается скриптом сверки ссылок (см. §9).

## 3. Уровни тестов

| Уровень | Название | Среда | Инструменты | Когда выполняется |
| --- | --- | --- | --- | --- |
| L0 | Static / Contract | CI | typecheck, schema-валидация IPC-каналов, секрет-скан репозитория, markdown/i18n lint | каждый коммит |
| L1 | Unit | CI | Vitest, fast-check (property-based) | каждый коммит |
| L2 | Integration | CI | main-процесс с фейковыми системными границами (fake PowerShell, fake child process, in-memory fs), renderer↔main через тестовый IPC-мост | каждый коммит |
| L3 | System E2E | Лаборатория Windows | реальные WFP/Wintun/DNS/AD, pktmon, сетевой эмулятор, NSIS-артефакты | nightly + перед релизом |
| L4 | Exploratory | Лаборатория | уставные сессии (charters) 60–90 мин с фиксированной целью | перед релизом |

Правило выбора уровня: проверка выполняется на **самом низком** уровне, где оракул остаётся достоверным. Утечку пакетов нельзя доказать на L1; инвариант парсера не нужно гонять на L3.

## 4. Таксономия типов тестов

Каждый тест помечается одним или несколькими типами. Набор типов — обязательная часть дизайна пакета: пакет без негативных и chaos-тестов считается незавершённым.

1. **Functional positive** — заявленное поведение на валидных данных.
2. **Negative / boundary** — границы диапазонов, пустые/максимальные значения, отказы.
3. **Abuse / security** — hostile IPC sender, подделка senderFrame, DNS rebinding (Host header), path traversal в импорте, инъекции в PowerShell-команды, подмена манифеста.
4. **Fault injection / chaos** — `taskkill /F`, отказ диска (disk full), пропажда DLL, блокировка реестра, отзыв прав администратора, обрыв питания VM (hard reset), зависание дочернего процесса (no-exit hang).
5. **State-machine model-based** — конечный автомат туннеля (`TunnelState`) как модель; генерация туров переходов (включая «недопустимые» команды в каждом состоянии) и проверка инвариантов после каждого шага.
6. **Property-based** — инварианты парсеров и сериализации на сгенерированных входах (fast-check, seed фиксируется в отчёте).
7. **Metamorphic** — когда эталона нет: `decode(encode(x)) ≡ x`; перестановка серверов в подписке не меняет итоговое множество профилей; повторный импорт того же файла идемпотентен.
8. **Fuzzing** — парсеры URI/JSON/YAML/Happ payload, IPC payloads; бюджет не менее 100k итераций или 10 мин на парсер в nightly.
9. **Pairwise config matrix** — попарное покрытие ОС × режим (Hard/Soft/Direct) × протокол × DPI-профиль вместо полного перебора.
10. **Performance budget** — бюджеты: холодный старт UI ≤ 3 с; подключение Hard TUN ≤ 15 с; простой CPU main-процесса ≤ 2%; RSS renderer ≤ 300 МБ после 1 ч; задержка IPC ping ≤ 50 мс p95.
11. **Soak / stability** — 24–72 ч: циклы подключение/ротация/отключение, периодическая выборка утечек, контроль роста handles/memory/GDI-объектов, отсутствие деградации latency.
12. **Upgrade / rollback** — миграции секретов и схем store при обновлении 1.1.x → next; откат прерванной установки; сохранность пользовательских данных.
13. **Accessibility (a11y)** — проход ключевых сценариев только с клавиатуры, screen reader (NVDA), focus trap/restore, контраст, `lang`-атрибут.
14. **Localization completeness** — CI-гейт: паритет ru/en ключей; непереведённая русская строка в UI = ошибка сборки.
15. **Observability assertion** — каждый L2/L3 тест проверяет не только результат, но и телеметрию: correlation id присутствует, событие записано в audit/event log, статус операции конечен (`success`/`error`, не «завис»).

## 6. Управление тестовыми данными

- **Фикстуры:** golden-наборы профилей каждого протокола (VLESS Reality, Hysteria 2, WireGuard endpoint, SS2022 SIP002, VMess, NaiveProxy), их повреждённые и граничные варианты, подписки размером 0/1/200/10 000 серверов, многоязычные и смешанные JSON/YAML/URI тексты.
- **Синтетические секреты:** все секреты в тестах имеют префикс-маркер `FAKE-`. Позитивный контроль: секрет-сканер обязан находить маркер — отсутствие находки означает поломку сканера, а не чистоту кода.
- **Запрещено** использовать реальные ключи, серверы и подписки в любых артефактах тестов и логах.

## 9. Регламент сверки покрытия

1. Скрипт извлекает все `AT-\d\d-\d\d\d` из файлов пакетов и все ссылки `AC-*` из их строк «Трассировка».
2. Сверка с `ac-inventory.csv`: каждый AC обязан встречаться хотя бы в одной трассировке. Список непокрытых AC — в отчёт сверки.
3. Отдельно сверяются ссылки `F-\d\d\d`: все подтверждённые находки журнала аудита обязаны быть покрыты; опровергнутые (F-151, F-162) имеют помеченный регрессионный тест.
4. Сверка запускается на каждом изменении `docs/04-приёмочные-тесты/` и документов требований.
