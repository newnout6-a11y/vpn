# WP-0. Контракты, инвентаризация и наблюдаемость — набор тестов

**Покрывает:** F-019, F-021, F-074, F-138, F-143; сквозные AC всех групп (единая модель состояния и конверт результата).
**Готово, когда:** любое действие имеет однозначный owner/state/result; повтор и отмена не создают гонку; ошибки и события коррелируются; UI не показывает переход как стабильное состояние.

---

### AT-00-001: Паритет IPC-контрактов main ↔ preload ↔ shared
**Трассировка:** F-138, WP-0, WP-1 · **Уровень:** L0 · **Тип:** contract
**Предусловия:** чекаут репозитория.
**Шаги:**
1. Извлечь список каналов из `shared/ipc-types.ts`, экспонированные методы preload (`contextBridge`) и зарегистрированные `ipcMain.handle`.
2. Сравнить три множества поимённо.
**Оракул (PASS, если все условия):**
- Три множества каналов совпадают точно; неэкспонированные и «осиротевшие» декларации отсутствуют.
- Каждый канал имеет схему входа и типизированный конверт результата (`ok/result/error`).
- Дрейф списков заваливает сборку с сообщением, указывающим расхождения поимённо.
**Очистка:** не требуется.

### AT-00-002: Model-based обход конечного автомата туннеля
**Трассировка:** F-019, F-021, WP-0, WP-2 · **Уровень:** L2 · **Тип:** state-machine model-based
**Фикстуры:** модель `TunnelState` со всеми состояниями и событиями (connect/disconnect/crash/timeout/cancel/retry).
**Шаги:**
1. Сгенерировать все туры переходов глубиной ≤ 6 из начального состояния (сеед фиксируется в отчёте).
2. В каждом состоянии дополнительно подать каждое недопустимое событие.
**Оракул (PASS, если все условия):**
- Каждый тур завершается в допустимом состоянии; недопустимые события отклоняются типизированной ошибкой без смены состояния.
- Инварианты после каждого шага: не более одного активного ядра; нет осиротевшего TUN; счётчик операций согласован с историей.
- «Переход» нигде не фигурирует как состояние, возвращаемое в UI.
**Очистка:** сброс in-memory стенда.

### AT-00-003: Отмена и deadline каждой долгой операции
**Трассировка:** F-021, WP-0 · **Уровень:** L2 · **Тип:** fault injection
**Шаги:**
1. Для каждой операции из реестра (connect, refresh, speed test, import, export, rotation): запустить, отменить на 10%, 50%, 90% выполнения (фейковые границы с управляемыми задержками).
2. После отмены выдать «поздний» callback из фейковой границы.
**Оракул (PASS, если все условия):**
- Каждая операция реагирует на `AbortController`/deadline не позднее 1 с.
- Поздние callbacks после отмены/shutdown не мутируют состояние и не пишут в историю (проверка по журналу событий).
- Статус операции конечен: `cancelled`/`error`, ни одна не остаётся «выполняющейся».

### AT-00-004: Таксономия ошибок на границе renderer
**Трассировка:** F-074, WP-0, WP-1 · **Уровень:** L2 · **Тип:** negative, contract
**Шаги:**
1. Спровоцировать каждую категорию ошибок (сеть, права, валидация, конфликт состояния, внутренняя) на каждом privileged канале.
**Оракул (PASS, если все условия):**
- Каждая ошибка мапится в типизированную категорию таксономии; renderer не получает сырых stack trace (проверка подстрок `at `, абсолютных путей в payload).
- Коды ошибок стабильны между прогонами и задокументированы.

### AT-00-005: Сквозная корреляция событий
**Трассировка:** F-143, WP-0 · **Уровень:** L2 · **Тип:** observability assertion
**Шаги:**
1. Выполнить одно действие пользователя (подключение), собрать все события audit/event log, IPC-ответы и записи истории.
**Оракул (PASS, если все условия):**
- Все события действия несут один correlation id; порядок событий монотонен по времени.
- Запись истории подключения содержит обязательные поля: источник, owner, route, достоверность результата.
- Ни одно событие не содержит секретов (прогон redactor-политики по полям).

### AT-00-006: Реестр миграций хранилищ
**Трассировка:** F-074, WP-0 · **Уровень:** L1 · **Тип:** functional, negative
**Шаги:**
1. Поднять store каждой исторической версии схемы (фикстуры), применить миграции вперёд до текущей.
2. Попытаться открыть store версии «из будущего» (version+1).
**Оракул (PASS, если все условия):**
- Миграции применяются строго по порядку, результат каждой зафиксирован; итоговая схема эквивалентна эталону.
- Версия «из будущего» отклоняется явной ошибкой без попытки записи; файл не модифицирован (сверка хэша).

### AT-00-007: Гонка «подключить/отключить» под спамом команд
**Трассировка:** F-021, WP-0, WP-2 · **Уровень:** L2 · **Тип:** race, model-based
**Шаги:**
1. Из 10 потоков подать 200 случайных команд connect/disconnect/cancel (fast-check, seeded).
**Оракул (PASS, если все условия):**
- Финальное состояние принадлежит {disconnected, connected} и согласовано с последней принятой командой.
- Ни один вызов не вернулся «успехом» для проигравшей гонку команды; все отказы типизированы.
- Ресурсы: 0 живых дочерних процессов при disconnected (сверка PID-реестра).

### AT-00-008: UI не отображает переход как стабильное состояние
**Трассировка:** F-019, WP-0, WP-9 · **Уровень:** L2 · **Тип:** functional, UI-contract
**Шаги:**
1. Прогнать state machine через все переходы, снимая снапшоты статусного компонента в каждом кадре.
**Оракул (PASS, если все условия):**
- Во время перехода статус помечен как нестабильный (индикатор прогресса), текст не содержит слова «переход» в label состояния.
- Ни один кадр не показывает «защита активна» до подтверждённого connected.

### AT-00-009: Фичефлаги плановых функций
**Трассировка:** WP-0, WP-12 · **Уровень:** L0/L2 · **Тип:** contract
**Шаги:**

### AT-00-010: История операций устойчива к повреждению
**Трассировка:** F-143, WP-0 · **Уровень:** L2 · **Тип:** fault injection
**Шаги:**
1. Записать 100 событий истории; повредить файл (обрезать, подменить хвост мусором); перезапустить.
**Оракул (PASS, если все условия):**
- Файл восстановлен из backup либо честно помечен повреждённым; молчаливая потеря истории недопустима — событие `history.corrupted` присутствует.
- После восстановления запись новых событий работает.
