# WP-3. Firewall, baseline, адаптеры, DNS и recovery — набор тестов

**Покрывает:** F-016, F-017, F-030…F-044, F-146, F-147, F-150, F-152, F-202…F-205; AC-LEAK-001…004, AC-LEAK-KS-001…005, AC-LEAK-NET-001…005, AC-LEAK-RCV-001…004.
**Среда по умолчанию:** L3 на полной OS-матрице (OS-W10-22H2, OS-W11-23H2, OS-W11-24H2); сетевые профили NET-BASE, NET-FLAP, NET-IPV6-ONLY.

---

### AT-03-001: Kill-switch при разрыве туннеля — двойной оракул утечек
**Трассировка:** AC-LEAK-KS-001…005, F-030, F-031, WP-3 · **Уровень:** L3 · **Тип:** chaos, security, dual-oracle
**Среда:** OS-W11-24H2; pktmon на физическом адаптере; зеркальный порт/внешний наблюдатель.
**Шаги:**
1. Активировать защиту с kill-switch; генерировать фоновый трафик (HTTP-пинги 10/с, DNS-запросы, попытки WebRTC).
2. Насильственно разорвать туннель: убить ядро, заблокировать сервер на маршрутизаторе, выдернуть кабель на 5 с (NET-FLAP).
3. Продолжать генерацию 60 с после разрыва.
**Оракул (PASS, если все условия):**
- Внутренний оракул: счётчики WFP-фильтров блокировки > 0, разрешающих транзитных фильтров вне туннеля нет.
- Внешний оракул: в захвате pktmon за окно 60 с — 0 пакетов с payload приложения вне туннельного интерфейса; 0 DNS-запросов к системному резолверу.
- UI в течение ≤ 2 с отражает потерю туннеля и никогда не сообщает «защищено».

### AT-03-002: Boot recovery после жёсткого убийства (F-202…F-205)
**Трассировка:** AC-LEAK-RCV-001…004, F-032, F-202, F-203, F-204, F-205, WP-3 · **Уровень:** L3 · **Тип:** chaos, recovery
**Шаги:**
1. Активная защита с системными изменениями. `taskkill /F` main-процессу и всем дочерним (симуляция крэша без cleanup).
2. Перезагрузить Windows; задача Boot Recovery выполняется от SYSTEM.
**Оракул (PASS, если все условия):**
- Задача зарегистрирована корректной командой schtasks (F-203), скрипт находится по заявленному пути (F-202), манифесты читаются только из ACL-защищённого ProgramData (F-205).
- После загрузки сеть восстановлена к baseline: 0 осиротевших правил WFP/файрвола, адаптеры Wintun обработаны (F-204: отсутствующий Wintun — не ошибка, а ветка сценария).
- Результат recovery записан и показан в UI при следующем запуске.

### AT-03-003: Матрица «манифест отсутствует / повреждён / частичный»
**Трассировка:** F-033, F-034, WP-3 · **Уровень:** L2/L3 · **Тип:** fault injection matrix
**Фикстуры:** (a) манифест удалён; (b) JSON повреждён; (c) половина шагов без подписи; (d) version схемы не поддерживается.
**Шаги:** для каждой фикстуры выполнить boot recovery и обычный rollback.
**Оракул (PASS, если все условия):**
- (a) Возврат в `Allow`, статус `unknown`, обязательное предупреждение в UI — «тихого успеха» нет.
- (b) Безопасный дефолт + диагностическое событие; повреждённый манифест карантинирован, не исполнен.
- (c) Неподписанные шаги не исполняются; выполнены только валидные; отчёт по каждому шагу.
- (d) Отказ с явной ошибкой версии; сетевое состояние не изменено.

### AT-03-004: Сосуществование с чужими правилами файрвола
**Трассировка:** F-035, F-036, WP-3 · **Уровень:** L3 · **Тип:** compatibility, negative
**Шаги:**
1. До установки создать пользовательские правила Block и Allow (порт 8080, программа test.exe).
2. Применить и снять защиту трижды.
**Оракул (PASS, если все условия):**
- Пользовательские правила побайтово идентичны после каждого цикла (экспорт `netsh advfirewall export` + diff).
- VPNTE модифицирует только собственные правила (маркировка по имени/группе); полный откат возвращает ровно исходный набор.

### AT-03-005: Нет физического адаптера — без ложного успеха
**Трассировка:** F-037, AC-LEAK-NET-001, WP-3 · **Уровень:** L3 · **Тип:** negative
**Среда:** VM с отключёнными всеми физическими NIC.
**Шаги:** включить защиту.
**Оракул (PASS, если все условия):**
- Lockdown пустого множества адаптеров не сообщается как успех; статус `not-checked`/ошибка с объяснением.
- Ни одно правило не создано «в пустоту»; попытка зафиксирована в журнале.

### AT-03-006: Изменение адаптеров во время применения
**Трассировка:** F-038, F-039, WP-3 · **Уровень:** L3 · **Тип:** chaos
**Шаги:**
1. Во время apply-фазы: отключить/включить NIC, подключить USB-модем, переименовать адаптер.
**Оракул (PASS, если все условия):**
- Операция либо корректно адаптируется к новому набору адаптеров (динамический alias-discovery), либо откатывается полностью; «висячих» фильтров на несуществующие интерфейсы нет (проверка `Get-NetFirewallFilter`).
- Итоговый статус отражает фактическое покрытие адаптеров.

### AT-03-007: Частичный отказ шагов rollback (F-148)
**Трассировка:** F-040, F-148, WP-3 · **Уровень:** L2 · **Тип:** fault injection matrix
**Шаги:**
1. Откат из N=8 шагов; инжектировать отказ в шаг k для k = 1…8 (фейковые системные границы).
**Оракул (PASS, если все условия):**
- При отказе шага k шаги k+1…N выполняются (независимость шагов); результат каждого шага явный.
- UI получает сводку с перечнем неудачных шагов и рекомендацией; общий статус — не «успех».
- События всех шагов с correlation id присутствуют.

### AT-03-008: Конкурентное изменение активных исключений
**Трассировка:** F-041, F-146, WP-3 · **Уровень:** L2 · **Тип:** race
**Шаги:**
1. Пока исключение активно, из двух «потоков» (UI + планировщик) изменить его одновременно 50 раз seeded.
**Оракул (PASS, если все условия):**
- Изменение либо применено сразу атомарно, либо помечено «будет применено при следующем запуске» — согласно решению владельца; промежуточных рассинхронизированных состояний нет.
- Ни одно обновление не потеряно молча; финальный набор исключений согласован с журналом операций.

### AT-03-009: Строгая валидация исключений файрвола
**Трассировка:** F-042, F-147, WP-3 · **Уровень:** L1 · **Тип:** property-based, negative
**Шаги:**
1. fast-check по генераторам: типы исключений, пути (canonical/нормализация `..`, 8.3-имена), IP/CIDR (маски /0…/32, IPv6), длины, дубликаты.
**Оракул (PASS, если все условия):**
- Невалидные значения отклонены с указанием поля; дубликаты детерминированно слиты или отклонены по правилу.
- Canonical path: `C:\PROGRA~1\…` и `C:\Program Files\…` распознаются как один путь.
- Дефолты нормализуются к документированным значениям.

### AT-03-010: Блокировка IPv6, включая обход NAT64/DNS64
**Трассировка:** AC-LEAK-NET-003…005, F-043, WP-3 · **Уровень:** L3 · **Тип:** security, negative
**Среда:** NET-IPV6-ONLY (NAT64/DNS64 на маршрутизаторе), мобильный тетеринг-профиль.
**Шаги:**
1. Активный kill-switch; попытки: прямой IPv6, Teredo/6to4/ISATAP туннели, DNS64-синтез через `ipv4only.arpa`.
2. Проверить собственный WFP sublayer и полный набор persistent/boot-time фильтров, включая disabled boot-фильтры после старта BFE. Для VPN-разрешений проверить совместные условия App ID + точный endpoint `/128` + LUID; отсутствие широкого автоматического разрешения NAT64-префикса или физического интерфейса.
3. На мобильном IPv6-only/464XLAT аплинке подтвердить рабочее VPN-соединение; повторить негативные попытки другим процессом к тому же endpoint и ядром к другому адресу. На время проверки не задавать пользовательские исключения и исключить документированный LAN из внешнего packet oracle.
4. После жёсткого убийства и SYSTEM reboot проверить отсутствие окна внешнего IPv6 egress до BFE и поведение обычного/strict recovery. Сохранить фильтры, pktmon и внешний capture как доказательства.
**Оракул (PASS, если все условия):**
- Весь неразрешённый IPv6-трафик вне туннеля заблокирован (pktmon: 0 пакетов); разрешён только документированный LAN и точный VPN-транспорт. Переходные механизмы отключены/блокированы согласно lockdown-манифесту; чужие Block не обходятся разрешением VPNTE.
- NAT64-обход не даёт egress: внешний наблюдатель фиксирует 0 сессий с реального IP.
- Снятие защиты восстанавливает исходную конфигурацию IPv6 побайтово.

### AT-03-011: Отказ DNS во время применения
**Трассировка:** F-044, WP-3 · **Уровень:** L3 · **Тип:** fault injection
**Среда:** NET-DNS-POISON → полный отказ DNS на середине apply.
**Оракул (PASS, если все условия):**
- Шаг DNS признан неуспешным; откат возвращает системный DNS к baseline; нет состояния «половина DNS переключена».
- Пользователю показана причина; повторная попытка после восстановления DNS успешна.

### AT-03-012: Recovery доверяет только подписанным ACL-манифестам
**Трассировка:** F-150, F-152, WP-3 · **Уровень:** L3 · **Тип:** abuse
**Шаги:**
1. Подложить поддельный манифест в непривилегированный каталог и в ProgramData с ослабленным ACL.
2. Перезагрузиться.
**Оракул (PASS, если все условия):**
- Поддельные манифесты проигнорированы; событие безопасности записано; сеть не изменена по данным атакующего.
- Легитимный манифест из доверенной области исполнен корректно.
