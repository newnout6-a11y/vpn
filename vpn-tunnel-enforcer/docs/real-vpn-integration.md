# Реальный VPN-сценарий на GitHub Actions

Прогон выполняется в отдельной одноразовой Windows на GitHub. Действующий VPN на компьютере разработчика не участвует. Локальный `npm run test:real-vpn` завершается отказом **до чтения профилей, PowerShell, запуска приложения или изменения сети**. Self-hosted runners также запрещены.

## Однократная настройка

В репозитории нужен Actions secret **VPNTE_REAL_SCENARIO**. Его значение — JSON со следующей структурой:

```json
{
  "schemaVersion": 1,
  "settings": {
    "connectionMode": "directVpn",
    "routingMode": "hard",
    "firewallKillSwitch": true,
    "strictAdapterLockdown": true,
    "publicWifiCompatibility": true,
    "autoNetworkBaseline": false,
    "adaptiveBypassEnabled": true,
    "autoPilotEnabled": true,
    "smartRuSplit": false,
    "proxyEngine": "auto"
  },
  "profiles": [
    { "input": "ПОЛНЫЙ URI ИЛИ JSON СЕРВЕРА A", "clientDevice": "pc" },
    { "input": "ПОЛНЫЙ URI ИЛИ JSON СЕРВЕРА B", "clientDevice": "pc" }
  ]
}
```

Значения выше показывают формат, а не настройки конкретного пользователя. Для воспроизводимого прогона нужно передать его настоящие настройки и два полных профиля. `settings` накладываются на defaults приложения; каждое переданное поле проверяется чтением после сохранения. Неуказанные поля остаются default — такой прогон нельзя называть точной копией пользовательских настроек. Отдельные хранилища правил, расписаний и исключений этим форматом не переносятся. Изменения инфраструктуры, маршрутов до сервера и версии Windows также влияют на время.

Каждый `input` должен импортировать ровно один сервер. Поддерживаются те же URI и полные JSON, что в обычном импорте приложения. Подписка с несколькими серверами отклоняется, чтобы A/B не менялись между прогонами. Копирование DPAPI-файлов с компьютера в runner не работает: импорт выполняется через production `serversAdd`, а ключи шифруются уже пользователем раннера.

Секрет можно сохранить через Settings → Secrets and variables → Actions или командой (без ключей в аргументах):

```powershell
Get-Content -Raw -LiteralPath 'путь-к-локальному-секретному-json' |
  gh secret set VPNTE_REAL_SCENARIO --repo newnout6-a11y/vpn
```

Сам тест ничего не экспортирует с компьютера и не загружает ключи в GitHub. Не коммитите JSON с настоящими ключами; для локальной подготовки используйте игнорируемую `.tmp/`. Размер секрета ограничен 48 KiB. Передача ключей внешнему сервису требует отдельного решения владельца.

## Запуск

После появления новых inputs в default branch: Actions → **CI** → Run workflow → включить **real_vpn**. Проверяемая ветка выбирается там же. До слияния можно запустить режим через уже зарегистрированный workflow CI, указав ветку с кодом:

```powershell
gh workflow run ci.yml --repo newnout6-a11y/vpn --ref ИМЯ-ВЕТКИ -f real_vpn=true -f cancel_after_ms=500
```

Обычный CI и PR не запускают реальные подключения и не получают этот secret. Ручной режим `real_vpn` запускает отдельный reusable workflow; обычные длинные CI-проверки в этом режиме пропускаются. Production-сборка и проверки тестового драйвера выполняются до передачи секрета в отдельный шаг. Прогон использует GitHub-hosted `windows-2022` с правами администратора. Никаких локальных ВМ или кликов по окну не требуется. Параллельный запуск не отменяет уже выполняющееся VPN-подключение.

Последовательность:

1. Подключиться к A.
2. Отключиться.
3. Начать подключение к A, дождаться принятой backend-операции, отменить и дождаться её завершения.
4. Подключиться к A.
5. Переключиться на B.
6. Начать переключение обратно на A, отменить и дождаться восстановления B.
7. Всё-таки переключиться на A.
8. Измерить TCP ping выбранного сервера тем же методом, что использует кнопка пинга.

`cancel_after_ms` — задержка после обнаруженного backend transition (по умолчанию 500 мс). Если операция завершилась до отмены, тест падает. Ответ «отмена принята» измеряется отдельно от фактического завершения исходной операции и восстановления соединения.

## Что проверяется

Приложение собирается обычными build-скриптами и electron-builder, с настоящими закреплёнными движками и Wintun; SHA-256 архивов проверяется. Сценарий вызывает обычные `startDirectVpn`, `stopTun`, `cancelTun`, `serversSelect`, `serversCancelSwitch` и `serversPingOne` через production preload и зарегистрированные IPC. Перед подключением сохраняются текущие настройки, как в Dashboard. Окно Electron скрыто; UI-автоматизации нет. Node inspector доступен только на случайном loopback-порту, принадлежность PID проверяется.

Тестовый EXE собирается с `requestedExecutionLevel=asInvoker`, поскольку сам job уже elevated, а `requireAdministrator` на общем EXE Chromium мешает запускать ограниченные GPU/renderer-процессы на hosted Windows (SBOX_ERROR_CREATE_PROCESS=18, затем 0x80000003). Это override только disposable CI-артефакта; release-конфигурация не меняется. Права проверяются и у драйвера, и независимым PowerShell readback, запущенным самим Electron main. В отчёте фиксируются `build.executionLevel` и `runner.elevatedMain`. Sandbox, графика и сетевые настройки приложения сохраняются. Из stderr публикуются только severity/sourceFile/sourceLine и числовой GPU-код, без текста сообщения.

Перед запуском проверяются отсутствие другого VPNTE-процесса и свежий userData. Существующий клиент не останавливается. На каждом шаге сверяются canonical snapshot, окончание transition и выбранный профиль. Независимый PowerShell-оракул читает CIM/NetAdapter: путь runtime, его PID/командную строку, состояние TUN и адреса. При отключении не должно остаться runtime-процессов или активного TUN. После сценария требуется подтверждённый приложением VPN egress.

В `finally` выполняется обычное отключение и проверка очистки. Даже если readback не прошёл, отдельно запрашивается main-owned shutdown с подтверждением. Принудительное убийство процесса не используется. Неподтверждённая очистка даёт FAIL; сама машина удаляется GitHub после job. На шаг сценария установлен предел 10 минут, на job — 35 минут. Смена маршрутов может временно прервать связь самого раннера с GitHub; локальный тест продолжает работу, а отчёт загружается после очистки при восстановленной связи.

## Результат

В Summary запуска — таблица времени каждого действия, подтверждения отмены и фактического завершения. Артефакт `real-vpn-<run>-<attempt>` хранится 7 дней и содержит только:

- `report.json`: SHA-256 сборки/настроек, времена, итоговые состояния, PID/TUN readback, canonical transitions, разрешённые события приложения/IPC и результат очистки.
- `progress.log`: тот же поток, что выводится в Actions во время выполнения: подготовка, начало/конец каждого IPC, отдельные ID конкурентных вызовов, проверки ОС, изменения состояния и результат очистки. Каждые 5 секунд ожидания печатаются имя операции и прошедшее время. У каждой строки есть UTC и монотонное время от начала прогона.

Во время работы также читаются журналы приложения. В общий поток проходят только известные сообщения IPC/TUN/Xray/firewall/PowerShell helper и числовые времена, включая разрешённые фазы. При подготовке видны количество/состояние окон, загрузка страницы приложения и crash-флаг, без URL или содержимого страницы. Драйвер выбирает полностью загруженную страницу приложения: пустое или постороннее окно не получает тестовые вызовы.

Завершение IPC содержит только булевы `success`/`cancelled` и каноническую категорию ошибки. Отказы IPC и фиксированные сообщения об ошибках TUN тоже сохраняются; ошибки файлов, прав и конфигурации получают фиксированную метку `errorKind`, без исходного текста исключения. Для защиты адаптеров сохраняются число адаптеров, `applied` и фиксированные метки отказов DNS/IPv6/реестра/переходных адаптеров; исходные warnings отбрасываются. При некорректном снимке приложение называет только невалидные поля; тест сохраняет эти фиксированные имена и числовые line/column стека без путей. После закрытия inspector итоговый сбор читает только файлы, чтобы ошибка диагностики не мешала записать результат и очистку.

Репозиторий публичный. В артефакты не загружаются userData, полные логи, URI, настройки с ключами, адреса серверов или публичные IP. Секрет передаётся только шагу сценария и не наследуется Electron/PowerShell после разбора.

Это проверка реального пути приложения и конфигурации на Windows Server в облачной сети. Она не воспроизводит физический ПК, Wi-Fi или DPI провайдера. Время шага заканчивается после IPC и до дополнительного CIM readback; это не время клика/готовности UI и не p95. Packet-capture утечек, reboot и вся матрица AT не засчитываются этим сценарием.

## Проверки самого тестового драйвера

Без переключения настоящего VPN:

```powershell
npm.cmd --prefix vpn-tunnel-enforcer run test:real-vpn:unit
```

Проверяются точная последовательность IPC, реальный транспорт и скрытый renderer Electron в безвредной фикстуре, запрет локального/self-hosted/PR-запуска, безопасные ошибки секрета, импорт ровно A/B, отмены, восстановление сервера и независимые оракулы. Проверки журналов требуют вывода start/heartbeat до завершения операции, совпадения файла с потоком, отдельных ID для connect/cancel и отсутствия секретных аргументов/результатов/ошибок. Эти проверки включены в обычный CI и не требуют серверных ключей.
