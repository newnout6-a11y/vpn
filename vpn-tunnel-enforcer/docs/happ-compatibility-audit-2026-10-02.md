# Совместимость с Happ: раздача с телефона, 02.10.2026

## Область и подтверждённые данные

Владелец подтвердил: на одной раздаче Happ работает, VPNTE не открывает иностранные сайты; на обычном Wi-Fi VPNTE работает. Это основание искать дефект нашего клиента. Исправление найденных потерь конфигурации одобрено владельцем в этой сессии. Пакеты: WP-4 (импорт) и WP-2 (движок), связанные проверки и диагностика. Документы нормативного ТЗ не изменены.

Двоичные файлы Xray установленного Happ и нашего клиента имеют одинаковый SHA-256 и сообщают Xray 26.7.28, commit `5ca6f4b`. Версия ядра не объясняет различие этих двух установок. В отличие от нашего прежнего преобразования, Happ документирует передачу полного Xray JSON в ядро: [официальное описание](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters). Это сравнение конкретной конфигурации; полного совпадения возможностей приложений не заявляем.

Подписка получена с существующей PC-идентичностью VPNTE, без записи в пользовательские настройки. Ответ содержит **10 полных Xray JSON**, каждый представляет составное подключение. Старый список разрозненных узлов не является количеством конфигураций, возвращённых провайдером. Секреты, URL подписки, идентификатор устройства и адреса серверов в этом отчёте не публикуются.

Диагностика до исправления показывала быстрый прямой TCP CONNECT к выбранному VPN-узлу (~105 мс) и таймаут HTTPS через Xray (3 секунды); обычные иностранные HTTPS-пробы также завершались таймаутом. Это локализовало сбой после установления прямого TCP, но не определяло единственную причину TLS/REALITY. Доступность российских сайтов при Smart RU не проверяет VPN-выход.

**После установки исправления `9df718a` владелец подтвердил, что раздача заработала.** Свежий `app.log`: в 20:09:24.783 МСК (`17:09:24.783Z`) эффективная конфигурация использует `preserved-xray-json`, fingerprint `firefox`, mux включён, 19 outbounds, 5 балансировщиков, 5 виртуальных маршрутов, вход через balancer. Это подтверждает работоспособность соединения после совокупной правки; отдельную причину среди fingerprint/mux/моста из этих данных выделить нельзя. ## Маршрутизация и границы защиты

У нас sing-box продолжает управлять TUN, DNS, Smart RU и правилами изоляции. Передавать весь provider JSON как runtime config нельзя: он содержит собственные слушатели и глобальные direct-исключения. Из него компилируется только граф VPN-подключения.

В выбранном графе сохраняются Hysteria и мосты, которые реально поддерживает наше существующее Xray. Это не добавляет новую самостоятельную экспериментальную интеграцию ядра. Наш SOCKS слушает только 127.0.0.1. Глобальные правила прямого выхода, API, DNS, слушатели и пути логов провайдера не импортируются. Отсутствующая зависимость, цикл, неподдерживаемый протокол, ссылка на файл сертификата/ключа или незашифрованный application fallback отклоняются. Не совпавшее с условным виртуальным маршрутом соединение блокируется.

`freedom` разрешён только внутри графа dialer: это физическое соединение **к зашифрованному VPN-узлу**, необходимое для последнего уровня моста. Выход приложений через такой fallback запрещён. Есть отдельный тест этого различия.

Наш существующий sing-box маршрут для процесса `vpnte-xray.exe` отправляет его сокеты в direct-out перед правилами DNS/QUIC/приложений. Поэтому вспомогательные адреса графа также имеют физический путь через этот маршрут; они не требуют разрешать прямой выход приложениям. Проверки генератора покрывают исключение процесса ядра. Свежие пробы подтверждают доступность выхода на раздаче; полный набор Windows L3 критериев остаётся отдельной приёмкой.

Native профиль выбирает Xray в Auto; принудительный sing-box выдаёт ошибку с указанием выбрать Auto/Xray. Одна URI-ссылка не переносит mux и граф: после одобренной дополнительной правки копирование и сохранение такого профиля автоматически используют полный JSON соединения.

## Дополнительные находки: исправлены после одобрения владельцем

Первоначально эти результаты расширенного изучения были отдельными предложениями. Последующей командой «исправляй что нашёл» владелец одобрил весь список, включая записанное расхождение с ТЗ-03 §2.3. Рабочие пакеты WP-10 / WP-4 и связанные границы WP-2; нормативные документы не изменены. Находки не объявляются отдельными доказанными причинами прежнего отказа.

| Приоритет | Находка и место | Почему имеет значение | Выполненное исправление |
| --- | --- | --- | --- |
| P1 | `adaptiveBypass.networkFingerprint`: только имя физического интерфейса и MAC | Обычный Wi-Fi и телефон на одной карте получали одинаковый ключ | HMAC учитывает NLA-профиль, GUID, шлюз и IPv4-подсеть; DHCP-адрес хоста и отключение IPv6 на dual-stack ключ не меняют. Запрос только читает сеть, ограничен 4 секундами. Неизвестная сеть не использует и не сохраняет обучение; после стабильных проб идентичность сверяется повторно |
| P1 | `adaptiveBypass.profileFingerprint`: только type/server/port/SNI | Изменение транспорта, REALITY, fingerprint или графа не меняло ключ | Канонический HMAC включает параметры соединения, transport/REALITY/obfs, device/fingerprint и native граф. Косметическое имя и локальные route-поля исключены. Ключ `v2` автоматически удаляет старое обучение. Сетевое переключение и отмена блокируют позднюю запись |
| P2 | URI XHTTP терял mode/extra | Native JSON не исправлял аналогичную URI | Parse → Xray → URI export сохраняет четыре режима и вложенный extra; сохранённые старые `transport.method` читаются как mode. Убрано двойное URL-декодирование, повреждавшее буквальные `%2F`. Auto выбирает Xray, принудительный sing-box отклоняется |
| P2 | gRPC multiMode ошибочно выводился из idle_timeout | Конфигурация могла получать другой режим | Явные gun/multi и multiMode true/false проходят импорт, runtime и экспорт. idle_timeout не включает multiMode. Неизвестные/противоречивые значения отклоняются; явный режим требует Xray |
| P2 | `sanitizeProxyOutbound` удалял non-REALITY multiplex | Исходная конфигурация менялась | Явный multiplex сохраняется для VLESS/VMess/Trojan/Shadowsocks; legacy mux нормализуется. Неподдерживаемые сочетания отклоняются. Четыре конфигурации проверены встроенным sing-box |
| P2 | Native граф невозможно передать одной URI | Экспорт мог потерять цепочку | Копирование/сохранение используют JSON с проверенным графом, mux, балансировщиками, observatory и policy. Нет API, слушателей, DNS, путей логов и глобальных direct-исключений провайдера. Повторный импорт и Xray preflight проверены; общий экспорт с JSON создаёт JSON-массив, сохраняя обычные URI как строки |

Поля NLA, SSID, шлюзы и исходные параметры профиля не пишутся в журнал обучения: сохраняются только HMAC, режим и сроки. TTL 30 дней и предел 24 записи сохранены. Новое событие `adaptive-bypass / learning decision` содержит только версию, факт известной сети, факт повторного использования и режим. Стабильное окно проверки связи и правило успешных проб не ослаблены. Границы отмены проверены при ожидающем запросе идентичности, смене сети и нового подключения.

Перевод транспорта проверен по [Xray gRPC](https://xtls.github.io/en/config/transports/grpc.html), [Xray XHTTP](https://xtls.github.io/en/config/transports/xhttp.html) и [sing-box multiplex](https://sing-box.sagernet.org/configuration/shared/multiplex/). Это исправление конкретных потерь; полного совпадения всех возможностей Happ и полного переноса произвольных таймаутов между ядрами не заявляем.

Happ дополнительно описывает настройки fragmentation/noise и управления приложением: [официальная документация](https://www.happ.su/main/dev-docs/app-management). Само наличие этих функций не доказывает, что они включены в успешном подключении владельца. MTU Happ равен 1500, наш адаптивный TUN уже пробовал 1280; уменьшение MTU само по себе не исправило старый отказ. Произвольно включать фрагментацию или менять сервер вместо восстановления исходной цепочки оснований нет.
