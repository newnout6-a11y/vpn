# Совместимость с Happ: раздача с телефона, 02.10.2026

## Область и подтверждённые данные

Владелец подтвердил: на одной раздаче Happ работает, VPNTE не открывает иностранные сайты; на обычном Wi-Fi VPNTE работает. Это основание искать дефект нашего клиента. Исправление найденных потерь конфигурации одобрено владельцем в этой сессии. Пакеты: WP-4 (импорт) и WP-2 (движок), связанные проверки и диагностика. Документы нормативного ТЗ не изменены.

Двоичные файлы Xray установленного Happ и нашего клиента имеют одинаковый SHA-256 и сообщают Xray 26.7.28, commit `5ca6f4b`. Версия ядра не объясняет различие этих двух установок. В отличие от нашего прежнего преобразования, Happ документирует передачу полного Xray JSON в ядро: [официальное описание](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters). Это сравнение конкретной конфигурации; полного совпадения возможностей приложений не заявляем.

Подписка получена с существующей PC-идентичностью VPNTE, без записи в пользовательские настройки. Ответ содержит **10 полных Xray JSON**, каждый представляет составное подключение. Старый список разрозненных узлов не является количеством конфигураций, возвращённых провайдером. Секреты, URL подписки, идентификатор устройства и адреса серверов в этом отчёте не публикуются.

Последняя доступная диагностика раздачи показывала быстрый прямой TCP CONNECT к выбранному VPN-узлу (~105 мс) и таймаут HTTPS через Xray (3 секунды); обычные иностранные HTTPS-пробы также завершались таймаутом. Это локализует сбой после установления прямого TCP, но не определяет единственную причину TLS/REALITY. Доступность российских сайтов при Smart RU не проверяет VPN-выход. Повтор подключения после нынешнего исправления ещё не выполнен.

## Маршрутизация и границы защиты

У нас sing-box продолжает управлять TUN, DNS, Smart RU и правилами изоляции. Передавать весь provider JSON как runtime config нельзя: он содержит собственные слушатели и глобальные direct-исключения. Из него компилируется только граф VPN-подключения.

В выбранном графе сохраняются Hysteria и мосты, которые реально поддерживает наше существующее Xray. Это не добавляет новую самостоятельную экспериментальную интеграцию ядра. Наш SOCKS слушает только 127.0.0.1. Глобальные правила прямого выхода, API, DNS, слушатели и пути логов провайдера не импортируются. Отсутствующая зависимость, цикл, неподдерживаемый протокол, ссылка на файл сертификата/ключа или незашифрованный application fallback отклоняются. Не совпавшее с условным виртуальным маршрутом соединение блокируется.

`freedom` разрешён только внутри графа dialer: это физическое соединение **к зашифрованному VPN-узлу**, необходимое для последнего уровня моста. Выход приложений через такой fallback запрещён. Есть отдельный тест этого различия.

Наш существующий sing-box маршрут для процесса `vpnte-xray.exe` отправляет его сокеты в direct-out перед правилами DNS/QUIC/приложений. Поэтому вспомогательные адреса графа также имеют физический путь через этот маршрут; они не требуют разрешать прямой выход приложениям. Проверки генератора покрывают исключение процесса ядра. Реальное прохождение этого пути на раздаче остаётся частью Windows L3 приёмки.

Native профиль выбирает Xray в Auto; принудительный sing-box выдаёт ошибку с указанием выбрать Auto/Xray. Экспорт такого профиля в одну URI-ссылку недоступен: URI не переносит mux и граф. Возможность полноценного JSON-экспорта — отдельная работа.

## Другие подтверждённые ограничения: пока не исправлены

Это результаты запрошенного расширенного изучения. Они не являются доказанной причиной текущего отказа и не входят в одобренную правку импорта.

| Приоритет | Находка и место | Почему имеет значение | Предлагаемая работа |
| --- | --- | --- | --- |
| P1 | `adaptiveBypass.networkFingerprint`: только имя физического интерфейса и MAC | Обычный Wi-Fi и телефон на одной карте получают одинаковый ключ обученного режима | Добавить приватный идентификатор сети/шлюза, учитывать переключение сети, проверить перенос и сброс обучения |
| P1 | `adaptiveBypass.profileFingerprint`: только type/server/port/SNI | Смена транспорта, REALITY, fingerprint или native графа не меняет ключ обучения; возможен повтор старого решения | Записано расхождение с ТЗ-03 §2.3: расширить канонический отпечаток, версионировать ключ, проверить инвалидирование. По правилу AGENTS требует отдельного согласования |
| P2 | URI XHTTP: parser записывает mode в transport.method, converter его не использует; extra не переносится полностью | Исправление native JSON не исправляет аналогичную URI-ссылку | Отдельный цикл parse → runtime → export с mode/extra и отрицательными случаями |
| P2 | Перевод gRPC: multiMode выводится из idle_timeout; исходное поле может теряться | JSON теперь идёт native, но преобразуемые ссылки остаются отличающимися | Проверить по документации ядра и добавить точный round-trip |
| P2 | `sanitizeProxyOutbound` удаляет multiplex у части non-REALITY sing-box профилей | Отличие от исходной sing-box/Clash конфигурации остаётся вне native Xray пути | Отдельно проверить поддержку выбранного ядра и основания для удаления; записать предложение по ТЗ |
| P2 | Native полный JSON нельзя экспортировать одной URI | Обмен таким профилем требует исходной подписки; копия старого URI может лишиться цепочки | Добавить полноценный JSON-экспорт с теми же границами безопасности |

Happ дополнительно описывает настройки fragmentation/noise и управления приложением: [официальная документация](https://www.happ.su/main/dev-docs/app-management). Само наличие этих функций не доказывает, что они включены в успешном подключении владельца. MTU Happ равен 1500, наш адаптивный TUN уже пробовал 1280; уменьшение MTU само по себе не исправило старый отказ. Произвольно включать фрагментацию или менять сервер вместо восстановления исходной цепочки оснований нет.

## Как получить исправление

1. Установить новую сборку и выбрать Auto или Xray.
2. **Обновить подписку**: старые сохранённые плоские профили уже потеряли mux и мост; из старого outbound восстановить эти данные невозможно.
3. Выбрать нужную полную конфигурацию и подключиться через раздачу. В приложении должны остаться 10 конфигураций текущего ответа провайдера, а не набор разрозненных узлов.
4. Если сбой сохраняется, новое событие эффективной конфигурации и ранее добавленные проверки direct TCP / engine HTTPS, bootstrap DNS и сжатые хвосты логов дадут следующую измеряемую точку расследования.

В этой сессии приложение не устанавливалось и действующая сеть/фаервол/адаптеры не переключались. Успешную связь на раздаче после исправления пока не заявляем.
